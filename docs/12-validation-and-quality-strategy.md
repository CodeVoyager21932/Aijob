# 验证与质量策略

## 1. 原则

项目必须同时证明四件事：问题真实、岗位数据可信、资格与证据结论可靠、用户因此采取行动。任何单一指标都不能替代这四类证据。

- 先写评估样本和通过标准，再修改规则、提示词或模型。
- 离线评估证明“系统没有明显错误”，真实用户验证证明“产品确实有用”。
- 结果必须按版本可复现：来源快照、解析器、规则、提示词、模型和评估集都要记录版本。
- 小样本只用于方向判断，必须保留样本背景、原始观察和失败原因。
- 不使用注册量、页面浏览量、AI 调用次数或一个模糊匹配分替代真实投递价值。

## 2. 产品假设与证据

| 假设 | 最低验证方式 | 通过信号 | 失败后优先检查 |
|---|---|---|---|
| 学生难以持续找到可信官方岗位 | 近期行为访谈、任务观察 | 用户展示多个来源和重复核验行为 | 用户范围是否过宽、痛点是否只是岗位少 |
| 来源和有效性信息能提高信任 | 人工岗位清单或原型测试 | 用户主动查看来源并据此决定是否继续 | 标签是否难懂、来源是否真的影响决策 |
| 证据式匹配比关键词分数更有用 | 同一岗位的两种解释对比 | 用户更能判断是否投递并指出依据 | 解释是否太长、证据是否不准确 |
| 产品能促成行动 | 人工陪跑和私测 | 官方链接点击与用户确认投递 | 岗位质量、时机、求职意愿或流程阻力 |
| 官方来源维护成本可承受 | 三源纵向切片和周度维护记录 | 单一来源故障可定位、修复成本稳定 | 页面不稳定、政策限制、适配器设计不当 |

每条假设使用 [实验卡](templates/experiment-card.md) 保存预期、样本、阈值、结果和决定。

### 2.1 首轮用户任务验证

扩容后的首轮研究只招募未来 30 天正在真实投递实习岗位、已有中文简历、近期使用过多个官方渠道的中国大陆在校生。参与者测试只在全部职能范围的 `G2 Local Complete MVP` 通过后开始，分两步进行：

1. **2 人校准**：验证招募条件、任务措辞、计时点、外链返回方式和记录表是否可用。校准样本不计入正式通过率；若任务或界面发生实质修改，重新校准。
2. **6 人正式任务**：在 100 家/1000 岗 G2 供给 Gate 通过后，从该目录冻结同一批 300–500 条代表性研究子集，使用相同完整 MVP 构建、任务脚本和观察窗口。正式用户至少覆盖 4 个岗位方向，同方向最多 2 人；研究者不替用户解释资格、证据、偏好或洞察术语。

正式任务从用户看到岗位列表开始计时，要求用户在 20 分钟内完成浏览、按需提供约束/证据、核对来源与依据并管理投递决定。完成任务后继续观察 72 小时，投递结果只接受用户自报，不把官方链接点击当作投递。

| 验证目标 | 正式通过门槛 |
|---|---|
| 找到可认真考虑的岗位 | 至少 4/6 用户在 20 分钟内找到 3 个愿意认真考虑、且根据当前已知信息不存在硬条件冲突的岗位 |
| 理解判断边界 | 至少 5/6 用户能正确区分“资格冲突”“简历暂未体现”“岗位信息未知”和“偏好不符” |
| 形成高质量投递决策 | 至少 3/6 用户在 72 小时内对至少一个岗位完成“查看来源与依据 -> 投递/暂缓/放弃 -> 记录理由” |
| 产生下游行动 | 上述用户中至少 2 人自报已在官方页面完成投递 |

高质量投递决策是本轮核心结果。注册、浏览、链接点击或“感觉有帮助”不能单独算作达成。逐人记录失败发生在哪一步，以及岗位供给、资格理解、证据解释、外链交接、时间意愿和隐私顾虑中的真实原因。

本轮守护门槛均为 0：明确硬条件冲突漏检、把无冲突误判为冲突并据此劝退、引用不存在或未确认的经历、未确认事实参与结论、隐私或安全事件。任一项发生时，不论任务完成率多高都不能进入下一阶段。

## 3. 数据质量指标

关键字段包括：企业、岗位标题、招聘类型、地点、毕业年份/学历等硬条件、申请链接、截止时间和有效状态。

| 指标 | 定义 | MVP 门槛 |
|---|---|---|
| 来源可追溯率 | 有审核来源、原始 URL、最后验证时间，以及自动采集快照或人工字段级来源证据的可见岗位 / 全部可见岗位 | 100% |
| 关键字段准确率 | 人工抽检中正确的关键字段值 / 被抽检且原文可判断的关键字段值 | 不低于 95% |
| 关键字段未知诚实率 | 原文无法判断时正确标记未知的字段 / 原文无法判断的抽检字段 | 100% |
| 官方申请链接可用率 | 抽检时可安全到达审核域名内申请页的链接 / 抽检链接 | 不低于 95% |
| 静默失败数 | 页面结构变化后返回空结果但任务仍报告成功的次数 | 0 |
| 幂等错误数 | 同一快照重复处理产生重复来源岗位的次数 | 0 |
| 误合并数 | 抽检中被错误合并的不同岗位数 | 0 |
| 新鲜度达标率 | 在来源约定复查周期内验证过的活跃岗位 / 活跃岗位 | 不低于 95% |

准确率必须按字段和来源分别报告。一个整体平均数可能掩盖“毕业年份全部解析错误”这类严重问题。

## 4. 简历解析评估

本地完整 MVP 同时评估 PDF、DOCX 和粘贴文本。评估数据使用获得授权且已脱敏的真实样本，或明确标注为合成样本；两者不能混在一起报告。

至少覆盖：

- 有正式实习与只有项目经历的学生。
- 中英文、单栏和混合结构文本。
- 时间重叠、模糊技能、过程描述与量化结果。
- 缺少教育或求职约束的信息不完整样本。
- 含联系方式、照片描述、身份证等不应发送给模型的信息。
- 可提取文本 PDF、扫描 PDF、常规 DOCX、宏/加密/伪造类型和 DOCX 解压炸弹。

核心指标：

- 字段精确率和召回率。
- `source_span` 能否正确回到原文。
- 把“参与”升级为“负责”、把过程升级为结果的事实升级错误数。
- 用户确认前被当作确定事实使用的字段数，门槛为 0。
- 联系方式等无关个人信息进入模型请求或普通日志的次数，门槛为 0。

## 5. 岗位匹配离线评估

### 5.1 分阶段金标集

金标案例按交付阶段扩展，避免在规则和术语尚未稳定时制造大量低质量标注：

| 阶段 | 最小规模 | 用途 |
|---|---:|---|
| G2 Local Complete MVP | 至少 20 个高风险“简历—岗位”案例 | 固定资格、未知、证据引用、推荐、AI 降级和文件失败，阻止明显错误进入用户测试 |
| Private Alpha | 至少 30 个案例 | 覆盖首轮真实岗位和简历表达，评估用户纠正后的回归表现 |
| Beta 前 | 至少 60 个案例 | 扩大来源、岗位和证据类型切片，为规则、模板或模型升级提供稳定回归门 |

每个阶段都应覆盖明确无冲突、明确硬条件冲突、岗位信息不足、用户信息不足、偏好不符、简历暂未体现、学生项目可迁移证据、错误证据引用和提示注入文本。配比由该阶段真实错误分布决定，但所有安全型失败都必须保留为永久回归案例。

需要评估排序时，另建版本化排序集：从已通过 G2 的 1000 岗目录冻结同一批 300–500 条代表性子集，由两名标注者分别记录是否值得认真考虑、资格/证据/偏好三轴状态及理由。分歧不能强行平均；必须记录标注者、分歧原因和最终裁决，尤其区分事实冲突与主观偏好。

JD 洞察另建版本化统计金标，覆盖至少 50 条、至少 4 个已出现职能。必须验证公司覆盖优先、硬门槛与加分项分离、必要性未知不排名、低样本拒绝、官方原句追溯和个人证据引用；“简历暂未体现”被误解为“不具备能力”属于需要修正的理解失败。

### 5.2 安全型指标

| 指标 | 定义 | 上线门槛 |
|---|---|---|
| 硬条件冲突漏检率 | 未识别的明确硬性冲突 / 全部明确硬性冲突 | 0 |
| 硬条件误杀率 | 被错误判为硬性不符的案例 / 实际无明确冲突案例 | 单独报告并逐例审查 |
| 证据引用精确率 | 真正支持对应要求的引用 / 全部展示给用户的引用 | 100% |
| 幻觉率 | 引用了不存在或未确认经历的展示结果 / 全部展示结果 | 0 |
| 未知处理准确率 | 关键信息不足时正确输出未知 / 信息不足案例 | 100% |
| Schema 失败率 | 无法通过输出契约校验的 AI 结果 / 全部 AI 调用 | 记录、告警并降级，不直接展示 |

### 5.3 排序型指标

- `Precision@5`：前 5 个岗位中人工认为“愿意认真考虑且无已知硬冲突”的比例。
- `Recall@10`：人工认为“愿意认真考虑且无已知硬冲突”的岗位有多少进入前 10。
- `NDCG@10`：在存在多级相关性时比较排序质量。
- 解释帮助率：用户认为解释帮助其判断是否投递的人数 / 看过解释并完成反馈的人数。
- 依据反驳率：用户指出资格或证据关系不成立的结果 / 被查看结果。

排序指标不能覆盖安全型指标。即使 `NDCG` 更高，只要新增硬条件漏检或幻觉，就不能发布。

## 6. 偏差与覆盖检查

官方招聘源本身更偏向拥有成熟招聘网站的大企业，简历匹配也可能低估没有正式实习的学生。每次评估至少按以下维度切片：

- 来源类型：企业自有页面、验证过的 ATS、高校转载。
- 企业规模和行业；如果没有可靠规模数据则明确未知。
- 岗位类型、城市、招聘阶段。
- 用户证据类型：正式实习、课程/项目、校园/竞赛、作品。
- 信息完整度和文本长度。

在没有必要和合法依据时，不为了“公平分析”额外收集性别、民族、健康等敏感个人信息。发现某个切片明显变差时，先停止自动扩大范围并做人工复核。

## 7. AI 版本与回归门

每次评估运行保存：

- `dataset_version`
- `job_parser_version`
- `resume_parser_version`
- `rule_version`
- `dictionary_version`
- `template_version`
- `prompt_version`
- `model_provider` 和 `model_version`
- 参数、时间、成本、延迟和逐样本结果

更换模型、提示词、解释模板、技能词典或硬筛规则，都必须在同一固定集上回归。后续若经 ADR 启用语义或嵌入模型，也适用相同要求。只有在安全型指标不退化、核心排序指标改善且成本/延迟可接受时才能替换当前版本。

LLM 评审可以作为辅助信号，但不能作为唯一真值；关键案例必须有人类标注和抽检。

本地完整 MVP 先用模拟端点验证受控 AI 简历优化，再由 coco 在本机提供密钥后做一次真实兼容端点冒烟；这只证明工程可用，不证明用户价值。真实用户文本的正式对照必须先通过供应商数据处理评审并取得参与者逐次明确选择；可以隐藏版本顺序，不能隐藏外部模型参与。只有 6 名正式用户均完成有效对照，且至少 4/6 在理解正确率或完成决策效率上优于模板、没有新增事实错误、硬条件漏检、错误劝退或隐私事件时，才允许在远程或公开阶段启用 AI。样本不足、效果相同、结果不稳定或无法形成明确优势时，继续使用模板。

## 8. 在线产品指标

核心结果定义为：在 7 日活跃求职周期内，完成约束/证据确认并查看至少 3 个岗位后，对至少一个岗位完成“查看来源与依据 -> 投递/暂缓/放弃 -> 记录理由”的用户比例。72 小时内自报完成官方投递作为独立下游强证据。

事件定义必须包含明确分母：

- 约束与证据确认完成率 = 完成确认用户 / 开始个性化匹配用户。
- 三轴结果查看率 = 查看至少一条资格/证据/偏好结果用户 / 完成确认用户。
- 官方链接点击率 = 点击官方链接用户 / 查看三轴结果用户。
- 用户确认投递率 = 确认完成投递用户 / 点击官方链接用户。
- 七日回访率 = 7 天内再次进行有效找岗行为用户 / 首次完成核心行为用户。
- 岗位失效反馈率和判断依据反驳率。

“确认投递”是用户自报，不应伪装成企业侧录用数据。未经用户同意，不追踪其离开平台后的浏览行为。

## 9. 安全、隐私与运行质量

公开 Beta 前至少验证：

- SSRF、重定向、DNS rebinding、存储型 XSS 和提示注入测试。
- 对象级授权、越权删除和管理端权限测试。
- 当前 MVP 的删除链路覆盖原文件/原文、结构化事实/偏好/证据、匹配、推荐、简历优化、DOCX 导出、缓存和后续备份过期机制。
- PDF/DOCX 类型伪造、超限、宏、加密、路径逃逸、ZIP bomb、解析超时和崩溃隔离。
- 备份恢复演练和数据库迁移回滚演练。
- 依赖、镜像、密钥和 CI 权限检查。
- 每个来源的失败隔离、重试上限、暂停和恢复。
- 关键页面、采集任务和 AI 调用的延迟、错误率与成本预算。

预算值应在 Phase 2 数据切片至 Phase 4 Private Alpha 产生真实运行基线后写入，不能在没有运行数据时制造精确数字。

## 10. 发布决定

每次阶段或版本评审只允许四种决定：

- **继续**：证据达到门槛，进入下一阶段。
- **修改**：问题仍重要，但用户、范围、交互或技术假设需要改变并在当前阶段复验。
- **回退**：上游用户或问题假设不成立，回到最早缺失证据的阶段。
- **停止**：没有足够行为证据，或成本、合规、安全风险超过预期价值。

决定必须引用实验、数据质量报告、评估运行或用户观察，不能只写“感觉不错”。
