# MVP 路线与阶段门

## 1. 路线目标

MVP 不是先把抓取、搜索、AI、管理端全部做齐，而是按风险顺序证明一条核心链路成立：

```text
目标用户确实被当前找岗方式困扰
  -> 可信岗位与证据解释会改变投递决定
  -> 少量官方来源可以持续、合规地维护
  -> 最小产品能稳定完成端到端链路
  -> 用户会真实投递并再次使用
```

路线同时维护四条证据线：

- 用户证据：问题真实、高频且有行动后果。
- 数据证据：岗位来源可追溯、信息准确、链接有效。
- 产品证据：推荐帮助用户判断并采取投递行动。
- 工程证据：系统可测试、可观察、可删除数据、可安全回滚。

任何阶段未达到退出门时，应修改假设、样本或方案，而不是靠增加功能和岗位数量掩盖问题。

## 2. 当前首要用户与范围假设

首要用户暂定为：

> 正处于未来 1-3 个月实习或校招投递期、已有一份基础简历，但需要在多个企业官网和高校就业渠道之间找岗并判断是否值得投递的在校生或应届生。

首批样本暂定为产品、运营、内容和 AI 应用相关实习/校招岗位。该人群和岗位方向都是待验证假设，不是永久定位。

MVP 始终遵守以下边界：

- 只使用经过审核的企业官方招聘网站、高校就业网站和企业公开招聘页面。
- 不抓取 BOSS、实习僧、牛客等综合平台。
- 不绕过登录、验证码、访问控制或明确禁止的访问边界。
- 不自动批量投递，推荐终点是官方投递页。
- 不使用未知小型招聘项目作为运行底座。

## 3. Phase 0：用户发现

### 目标

先确认首要问题究竟是岗位分散、真假与时效、资格判断、经历匹配，还是投递准备，避免用完整技术方案替代问题验证。

### 工作与产出

- 访谈 8-12 名最近 30 天真实找过实习或校招的用户。
- 至少观察 5 次真实找岗过程或复盘浏览、收藏、表格与投递记录。
- 分别记录在校生与应届生，不提前合并结论。
- 形成脱敏研究记录、用户分群、问题排序和假设登记表。
- 明确用户当前替代方案及切换成本。

### 退出门

- 至少一个清晰用户分群反复出现同一高优先级问题。
- 用户能提供近期真实行为证据，而不只是表示“这个想法不错”。
- 至少 5 名目标用户愿意带真实求职需求参加下一阶段。
- 已确定当前最先验证的 1-2 个高风险假设。

如果用户只是觉得岗位分散，但这并不影响判断或投递，应修改价值主张，不能直接进入开发。

## 4. Phase 1：人工礼宾验证

### 目标

在没有爬虫、账号系统和完整界面前，用人工服务验证“可信岗位 + 资格判断 + 经历证据解释”是否真的改变用户行动。

### 最小实验

- 人工整理 20-30 条已确认有效的官方岗位，保留原始链接、来源、验证时间和硬条件。
- 邀请 5-8 名目标用户提供去标识化简历文本和求职约束。
- 使用固定模板人工生成 5-10 条推荐，AI 只能辅助整理，最终资格与证据由人工复核。
- 记录用户查看顺序、质疑点、放弃原因、官方链接点击和自报投递。
- 对比“只有岗位列表”和“带证据解释的推荐”，判断解释是否提供新增价值。

### 退出门

- 大多数参与者找到至少一个愿意认真考虑的岗位。
- 至少 3 名用户根据结果进入官方页面，并自报完成投递或明确开始准备投递。
- 用户能复述推荐理由，并指出哪些证据、缺口或未知项影响了决定。
- 至少一项原有产品假设被否定或被实质修改。
- 用户愿意在下一次真实找岗任务中再次接受同类服务。

未达到退出门时，优先修正用户、岗位样本或价值主张，不开始自动化建设。

## 5. Phase 2：三来源数据可行性

### 范围

只选择 3 个经过审核且结构有代表性的来源，每个来源先人工记录 5 条岗位：

1. 有公开 API、JSON 或结构化 ATS 的企业来源。
2. 有 JSON-LD 或稳定 HTML 的企业招聘页。
3. 一个发布逻辑不同的高校就业网或公开招聘页面；如必须绕过访问控制，则更换来源。

### 工作与产出

- 完成来源准入记录、域名白名单和岗位字段字典。
- 自行实现 3 个独立适配器及固定 HTML/JSON 测试夹具。
- 保存来源记录、原始快照、规范化岗位和解析版本。
- 连续复查两周，记录结构变化、失败原因、字段准确率和维护工时。
- 验证单个来源失败不会影响其他来源，也不会误关全部历史岗位。

### 退出门

- 可见岗位来源可追溯率为 100%。
- 核心字段人工抽检准确率不低于 95%。
- 官方投递链接可访问率不低于 95%。
- 适配器失败会显式告警，不会把失败伪装成“成功但没有岗位”。
- 已获得真实维护成本数据，并确认增加少量来源仍可承受。
- robots、使用条款、页面访问方式和展示范围均已记录，没有未处理的高风险边界。

此阶段不以 10-20 个来源或 100-300 条岗位为目标；先证明三个代表来源能持续维护。

## 6. Phase 3：工程纵向切片

### 目标

实现一条薄而完整、可以真实操作和测试的用户链路：

```text
1 个官方来源
  -> 岗位入库
  -> 列表与详情
  -> 粘贴去标识化简历文本
  -> 用户确认证据
  -> 规则优先的资格与证据匹配
  -> 可解释推荐
  -> 官方投递链接
  -> 用户反馈
```

### P0 范围

- 岗位列表、详情和少量核心筛选。
- 来源、最后验证时间、有效状态和官方原始链接。
- 仅支持粘贴简历文本；PDF/DOCX 文件上传另行通过安全评审后再开放。
- 用户确认的 `ResumeEvidence` 与可追溯的 `JobRequirement`。
- 先执行毕业年份、学历、地点、到岗时间等硬条件规则，再做证据对应。
- 输出“优先考虑、有限条件考虑、信息不足、硬性不符”及其依据。
- AI 仅解释已有要求、证据、缺口与未知项，失败时可降级到规则和模板结果。
- 简历原文、结构化证据及相关派生数据可删除。
- 初期运营可使用受保护脚本和质量报告，不要求先做完整管理后台。

### 工程门槛

- 已知硬条件冲突的固定测试集漏检率为 0。
- 推荐解释引用真实 `requirement_id` 和 `evidence_id`，不存在虚构经历。
- 信息不足时输出未知，不强行给高分或推荐。
- 来源失败、AI 失败和删除请求均有可测试的失败/降级路径。
- 关键链路有自动测试、日志与版本标识，可在测试环境重复运行和回滚。
- 5-10 名目标用户无需讲解即可完成“找岗 -> 看依据 -> 前往官方页”的任务。

通过第一条链路后，再把 Phase 2 的另两个来源接入同一管线；不先横向铺开所有模块。

## 7. Phase 4：私测 Alpha

### 样本

- 20 名符合首要用户定义的测试者。
- 至少 10 人确认简历证据和求职约束。
- 至少 5 人根据推荐进入官方页面并自报完成投递。

### 核心指标

- 简历/约束确认完成率。
- 推荐结果到官方投递页的点击率。
- 查看推荐后自报真实投递的用户比例。
- 用户认为推荐理由“可理解且有帮助”的比例。
- 一周内再次使用率。
- 无效岗位、硬条件、证据引用、排序、交互和隐私顾虑的错误分布。

### 守护指标

- 无效岗位率和官方链接失效率。
- 明确硬条件冲突漏检率。
- 无证据解释或虚构经历数量。
- 简历删除失败、安全事件和隐私投诉数量。

### 退出门

- 已确认哪个细分用户、哪些岗位类型和哪些解释机制稳定产生投递价值。
- 主要失败模式可复现并有清晰修正优先级。
- 数据、推荐、安全和删除链路均达到既定门槛。
- 至少出现真实复用行为，而不只是一次性体验或礼貌性好评。

不使用注册量、页面浏览量、岗位总数或 AI 调用次数代替真实投递价值。

## 8. Phase 5：Beta 与来源扩展

只有私测 Alpha 证明核心链路成立后，才逐步扩展：

- 将来源从 3 个增加到约 10-20 个，每批只增加结构相近、维护方式明确的一小组。
- 将经过抽检的有效岗位扩大到约 100-300 条。
- 根据真实查询和零结果数据扩展职能、城市和招聘类型。
- 在确有高频运营需求时建设来源健康、人工审核和异常处理界面。
- 在隔离解析、恶意文件测试和数据删除验证通过后，灰度开放 PDF/DOCX。
- 用发布门、监控、回滚和用户反馈决定是否继续扩大公开范围。

### 扩展门槛

- 新来源不会显著拉低字段准确率、链接有效率或响应时效。
- 单来源维护工时和单用户服务成本处于可承受范围。
- 增加岗位供给确实改善目标用户的有效推荐，而不只是增加列表长度。
- 公开上线所需的安全、隐私、合规、备份恢复和故障处理均已验证。

## 9. 暂停、回退与停止条件

出现以下情况时暂停扩展，并回到对应阶段：

- 找不到反复出现且会影响投递的高优先级用户问题。
- 人工礼宾结果不能改变用户判断或带来真实投递行动。
- 官方来源频繁变化，持续维护成本超过用户价值。
- 岗位有效率或字段准确率无法稳定达到门槛。
- 推荐经常违反硬条件、引用错误证据或制造虚假经历。
- 用户只浏览不投递，且经验证并非岗位样本不足。
- 当前隐私、安全或合规方案不能保护简历和来源边界。
- 为继续扩张必须绕过登录、验证码或访问控制。

回退不是失败，而是避免把错误假设自动化和规模化。

## 10. 每阶段必须保留的证据

- 脱敏访谈、任务观察和实验结果。
- 假设变化、关键取舍和必要 ADR。
- 来源准入、字段字典、适配器夹具和数据质量抽检。
- 功能规格、验收条件、测试和发布记录。
- 安全、隐私、删除、恢复与回滚验证。
- 用户点击、投递、复用和失败原因的最小必要数据。

没有真实用户和运行证据前，只能描述为“设计中”“实现中”或“验证中”，不能宣称产品已经成熟或得到市场验证。
