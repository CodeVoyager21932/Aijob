# 产品定义

> 当前状态：本文描述的是**待验证的产品假设**，不是已经得到市场验证的结论。目标用户、首要痛点和定位都应随访谈、人工礼宾实验和真实投递行为更新。

## 1. 当前定位假设

面向学生和应届生优先的可信求职决策平台：聚合经过审核的官方岗位来源，解析岗位要求和用户真实经历证据，帮助用户判断哪些岗位值得投递，并解释资格、支持证据、能力缺口和下一步行动，最终回到企业官方页面投递。

产品不是为了“再做一个岗位信息流”，而是尝试缩短这条决策链：

```text
分散的官方岗位
  -> 可追溯且仍有效的机会
  -> 我是否有资格
  -> 我的经历能否支持要求
  -> 是否值得投入时间
  -> 前往官方页面投递
```

## 2. 首要用户假设

产品发现阶段建议只研究一个首要用户群：

> 未来 1-3 个月处于真实实习或校招投递期、已有一份基础简历，但需要在多个官方渠道之间找岗并判断是否值得投递的在校生或应届生。

选择这一人群的原因是任务正在发生、行为容易观察，也能同时检验来源分散、资格判断和经历匹配三个风险。它仍然是候选细分，不应在用户研究前永久锁定。

长期可能服务的人群如下，但不同时进入 MVP：

| 阶段 | 用户 | 是否进入当前验证 |
|---|---|---|
| 首要用户 | 处于真实投递期、已有基础简历的在校生/应届生 | 是 |
| 后续候选 | 方向尚不清晰、没有基础简历的学生 | 否，需要职业探索能力 |
| 后续候选 | 毕业 1-3 年的初级求职者 | 否，需要更复杂的经验迁移判断 |
| 长期候选 | 其他社会求职者 | 否，需要更广来源和更复杂的岗位模型 |

底层数据模型可以兼容实习、校招、管培生、初级社招和普通社招，但不能以“未来兼容”为理由扩大当前功能范围。

## 3. 首要问题假设

用户真正要完成的不是浏览更多岗位，而是可靠地回答：

1. 这个岗位是谁发布的，现在是否仍然有效？
2. 我是否满足毕业年份、学历、地点、到岗时间等硬性条件？
3. 我的哪些真实经历能够支持岗位要求？
4. 这个机会是否值得我投入定制简历和投递时间？
5. 如果决定投递，下一步应突出或补充什么？

目前还不能假设这五个问题同样重要。访谈和实验需要识别其中最高频、后果最严重且现有方案解决不好的首要问题。

## 4. 当前替代方案与切换障碍

| 当前做法 | 对用户的价值 | 可能仍未解决的问题 | 使用本产品的切换障碍 |
|---|---|---|---|
| 综合招聘平台 | 岗位量大、搜索方便、使用习惯成熟 | 来源与时效需要再次核验 | 用户未必愿意牺牲覆盖量 |
| 企业官网、高校就业网、公众号 | 接近原始发布方 | 来源分散、格式不同、重复检查耗时 | 用户已有收藏夹和固定巡检习惯 |
| Excel、Notion、飞书表格 | 灵活记录收藏和投递状态 | 依赖人工整理，不能自动解释资格与证据 | 迁移已有记录需要成本 |
| 学长学姐、社群、付费辅导 | 有经验判断和情境建议 | 覆盖有限、质量不稳定、难以持续 | 人的信任可能高于自动推荐 |
| 通用 AI 或简历工具 | 使用门槛低、能快速给建议 | 可能缺少实时岗位、来源追溯和证据约束 | 用户可能认为现有工具已经够用 |

产品必须证明自己能让用户更快、更有把握地完成真实投递，而不只是展示不同的信息组织方式。

## 5. 差异化假设

差异化不来自“用了 AI”，也不来自岗位数量，而来自三个可以被验证的产品约束：

- **来源可信**：只接入经过审核的企业官方招聘网站、高校就业网站和企业公开招聘页面，并保留原始链接与验证时间。
- **判断有证据**：先判断明确资格，再把岗位要求对应到用户确认过的经历；未知项保持未知，不用黑盒分数掩盖。
- **结果促进行动**：输出服务于投递决定，终点是官方投递页，不在平台内制造无限信息流或自动海投。

如果用户不在乎来源信息、证据解释没有改变投递行为，或维护官方来源的成本不可承受，就需要修改定位，而不是继续堆功能。

## 6. 产品承诺

### 6.1 可信

- 岗位来自审核后的官方或公开招聘来源。
- 每条岗位显示来源类型、原始链接、首次发现时间和最后验证时间。
- 岗位失效、页面异常和信息不完整必须明确标记，不能静默伪装为有效。

### 6.2 可解释

- 不把缺乏依据的“匹配度”作为主要结论。
- 推荐理由必须引用具体岗位要求和用户确认过的简历证据。
- 明确区分“符合”“部分符合”“信息不足”和“硬性不符”。
- AI 只负责受约束的提取与解释，不能把推断或缺失信息写成事实。

### 6.3 帮助行动

- 推荐终点是企业官方投递页，而不是让用户继续停留在信息流。
- 输出投递前需要补充的材料、简历重点和风险提示。
- 后续可以记录投递结果，用真实反馈改善推荐，但不自动批量投递。

## 7. 验证范围

### 7.1 人工礼宾实验先验证价值

在开发完整产品前，先用人工确认的官方岗位、去标识化简历文本和固定匹配模板回答：

- 用户是否愿意提供必要的求职约束和简历文本？
- 来源与验证时间是否会改变用户对岗位的信任？
- 带证据的资格和经历判断是否会改变投递选择？
- 用户是否真的进入官方页面并完成或准备投递？

人工完成工作不代表产品失败；这一阶段的目标就是用最低成本淘汰错误假设。

### 7.2 工程 MVP 再验证可重复交付

只有价值信号成立后，才实现最小工程闭环：

```text
少量审核来源
  -> 岗位入库与有效性标记
  -> 简单列表和详情
  -> 用户粘贴简历文本并确认经历证据
  -> 规则优先的资格与证据匹配
  -> 可解释推荐
  -> 官方投递链接和最小反馈
```

工程 MVP 必须验证：

- 少量官方来源能否稳定采集、复查并以可接受成本维护。
- 岗位字段能否准确标准化、分类和去重。
- 用户简历文本能否转换为带出处且可确认的能力证据。
- 系统能否排除明确硬性不符岗位，并给出可理解的推荐理由。
- 工程化交付是否保留了人工实验中真正影响用户行动的部分。

## 8. 当前明确不做

- 抓取 BOSS、实习僧、牛客等综合招聘平台。
- 自动批量投递、模拟登录、绕过验证码或访问控制。
- 企业招聘管理、人才库或招聘方主动搜索用户。
- 社交社区、课程商城、职业测评大全和无目标职业探索。
- 在首轮工程 MVP 中支持 PDF/DOCX 文件上传。
- 为早期运营开发完整管理后台；先使用受保护的脚本和质量报告。
- 用未知小型开源招聘项目作为运行底座。
- 为追求覆盖率接入无法说明来源或合规边界的数据。

## 9. 非目标

- 不是岗位数量最多的平台。
- 不是 AI 替用户做职业决定。
- 不是用简历关键词制造虚假高分。
- 不是把用户经历改写成不存在的成果。
- 不是把公开网页全文复制后重新包装。
- 不是证明技术栈或自动化能力有多复杂。

## 10. 工程 MVP 用户旅程

1. 用户选择城市、岗位方向、实习/校招类型和时间约束。
2. 用户浏览带来源与有效性标记的岗位列表和详情。
3. 用户粘贴去标识化简历文本，并确认或修改解析出的经历证据。
4. 系统先排除明确硬性不符岗位，再召回可能相关的岗位。
5. 用户看到推荐等级、岗位要求、支持证据、能力缺口和不确定项。
6. 用户选择是否前往企业官方页面投递。
7. 用户可以反馈岗位失效、已经投递或推荐不准确，并可删除简历相关数据。

## 11. 指标与成立条件

### 核心结果指标

> 查看推荐后，在约定观察期内通过官方页面完成并自报真实投递的测试用户比例。

由于平台不能可靠获知企业官网中的最终提交，必须区分“官方链接点击”和“用户自报完成投递”，不能把前者冒充最终结果。

### 前置信号

- 用户完成求职约束和简历证据确认的比例。
- 用户从推荐进入官方投递页的比例。
- 用户能够复述推荐依据并认为其影响了决定的比例。
- 从提交输入到发现第一个愿意认真考虑岗位的时间。
- 一周内再次使用的测试用户比例。

### 守护指标

- 无效岗位率和官方申请链接不可访问率。
- 明确硬条件冲突漏检率。
- 无法追溯到岗位要求或简历证据的解释比例。
- 经历幻觉或把未知信息写成事实的次数。
- 用户数据删除失败、安全事件和隐私事件数。
- 单来源维护工时与单用户服务成本。

岗位总数、AI 调用次数和注册数不能替代上述结果指标。

## 12. 当前最高风险未知项

1. 用户的首要问题究竟是来源分散、资格判断、经历匹配还是投递行动不足。
2. 用户是否会因为“官方且可追溯”改变现有找岗路径。
3. 解释是否真的改变投递行为，而不只是让结果看起来更专业。
4. 用户是否愿意在明确的数据说明下提供去标识化简历文本。
5. 官方来源能否以可接受成本持续维护。
6. 规则与模板已经足够的部分，是否真的需要 AI。

这些未知项应通过 [产品发现与实验](09-product-discovery.md) 和 [从 0 到 1 的产品工程流程](08-zero-to-one-lifecycle.md) 逐项验证。
