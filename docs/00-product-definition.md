# 产品定义

## 1. 一句话定义

面向学生和应届生优先的可信求职决策平台：聚合经过审核的官方岗位来源，解析岗位要求和用户简历证据，推荐值得投递的企业岗位，并解释推荐理由、能力缺口和下一步行动。

## 2. 用户真正要完成的任务

用户不是为了“浏览更多岗位”，而是要连续完成以下任务：

```text
发现可信机会
  -> 判断自己是否有资格
  -> 判断是否值得投入时间
  -> 知道应该突出什么经历
  -> 回到企业官方页面投递
```

平台价值不以岗位数量为核心，而以四个问题能否被可靠回答为核心：

1. 这个岗位是谁发布的，现在是否仍然有效？
2. 我是否满足毕业年份、学历、地点、到岗时间等硬性条件？
3. 我的哪些真实经历能够支持岗位要求？
4. 如果决定投递，我下一步应该准备什么？

## 3. 目标用户

| 优先级 | 用户 | 主要困难 |
|---|---|---|
| P0 | 在校生寻找实习 | 信息分散、缺乏正式经验、不理解岗位要求 |
| P0 | 应届生参加校招 | 毕业年份和资格复杂、岗位更新快、投递时间紧 |
| P1 | 毕业 1-3 年的初级求职者 | 经历较少、方向不清、难以迁移已有能力 |
| P2 | 其他社会求职者 | 需要更广来源和更复杂的经验匹配 |

学生优先不等于产品永远只支持学生。底层数据模型需要兼容实习、校招、管培生、初级社招和普通社招，但 MVP 只选择有限来源和岗位样本验证。

## 4. 产品承诺

### 4.1 可信

- 岗位来自企业官方招聘网站、高校就业网站或企业公开招聘页面。
- 每条记录展示来源类型、原始链接、抓取时间和最后验证时间。
- 岗位失效、页面异常和信息不完整必须明确标记，不能静默伪装为有效。

### 4.2 可解释

- 不把一个缺乏依据的“匹配度”作为主要结论。
- 推荐理由必须引用具体岗位要求和简历证据。
- 明确区分“符合”“部分符合”“信息不足”和“硬性不符”。

### 4.3 帮助行动

- 推荐的终点是企业官方投递页，而不是让用户继续停留在信息流中。
- 输出投递前需要补充的材料、简历重点和风险提示。
- 后续版本可以记录投递结果，用真实反馈改善推荐，但不自动批量投递。

## 5. MVP 范围

### 5.1 必须验证

- 少量可信来源能否被稳定采集和持续复查。
- 岗位字段能否被准确标准化、分类和去重。
- 用户简历能否被转换为带来源的能力证据。
- 系统能否排除硬性不符岗位，并给出可理解的推荐理由。
- 用户是否会依据推荐进入官方页面并完成真实投递。

### 5.2 暂不实现

- 抓取 BOSS、实习僧、牛客等综合招聘平台。
- 自动批量投递、模拟登录、绕过验证码或访问控制。
- 企业招聘管理、人才库、招聘方主动搜索用户。
- 社交社区、课程商城、职业测评大全。
- 用未知小型开源项目作为运行底座。
- 为追求覆盖率接入无法说明来源或合规边界的数据。

## 6. 非目标

- 不是岗位数量最多的平台。
- 不是 AI 替用户做职业决定。
- 不是用简历关键词制造虚假高分。
- 不是把用户经历改写成不存在的成果。
- 不是把公开网页全文复制后重新包装。

## 7. 核心用户旅程

1. 用户选择城市、岗位方向、实习/校招类型和时间约束。
2. 用户浏览带来源与有效性标记的岗位。
3. 用户上传简历或粘贴简历文本，并确认解析结果。
4. 系统先排除硬性不符岗位，再召回可能相关的岗位。
5. 用户看到推荐等级、支持证据、能力缺口和不确定项。
6. 用户选择是否前往企业官方页面投递。
7. 用户可以反馈岗位失效、已经投递或推荐不准确。

## 8. 产品是否成立的判断

产品成立不以“网站上线”判断，而以三个证据判断：

- 数据证据：岗位来源可追溯、有效、低重复。
- 推荐证据：推荐没有明显硬条件冲突，解释能够回到原始文本。
- 用户证据：真实用户根据推荐完成投递，并愿意再次使用。
