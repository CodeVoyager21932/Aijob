# 简历解析与可解释匹配设计

## 1. 目标

匹配系统帮助用户判断“是否值得投递”，而不是替用户制造高分或替企业筛掉候选人。

所有结论必须建立在两个结构化对象上：

- 岗位要求：企业明确写了什么。
- 用户证据：用户确认的简历内容能够证明什么。

## 2. 简历证据模型

### 2.1 `ResumeEvidence`

每条证据包含：

| 字段 | 说明 |
|---|---|
| `evidence_id` | 唯一标识 |
| `evidence_type` | 教育、实习、项目、校园、竞赛、志愿、技能、证书 |
| `statement` | 结构化事实描述 |
| `source_span` | 对应简历原文位置 |
| `time_range` | 发生时间 |
| `skills` | 可由该经历支持的技能候选 |
| `outcome_type` | 过程、产出、定性反馈、量化结果 |
| `confidence` | 解析置信度 |
| `user_confirmed` | 是否经过用户确认 |

模型不能把“参与过”升级成“负责过”，不能把项目过程升级成业务结果。

### 2.2 用户约束与偏好

与简历证据分开保存：

- 毕业年份、学历、专业。
- 可到岗时间、每周出勤、可持续时长。
- 期望城市、是否接受异地或远程。
- 目标职能、行业偏好和排除项。
- 用户明确不接受的条件。

偏好不是能力，不能混入能力分数。

## 3. 岗位要求模型

`JobRequirement` 包含：

| 字段 | 说明 |
|---|---|
| `requirement_id` | 唯一标识 |
| `requirement_type` | 学历、专业、毕业年份、经验、技能、职责、语言、证书等 |
| `text` | 对应岗位原文 |
| `necessity` | 必须、优先、可选、未知 |
| `normalized_value` | 标准化值 |
| `confidence` | 提取置信度 |
| `source_span` | 岗位原文位置 |

“熟悉”“优先”“具备”“必须”等措辞不能被统一处理。无法确定必要性时标记未知，不自动升级为硬条件。

## 4. 三阶段匹配

### 4.1 第一阶段：硬条件判断

只使用确定性规则判断：

- 招聘类型和毕业年份。
- 学历下限。
- 明确限定的专业。
- 工作地点或远程条件。
- 到岗时间、每周出勤和实习时长。
- 明确要求的工作年限、语言或证书。

输出不是简单的通过/失败，而是：

- `eligible`：没有已知硬性冲突。
- `ineligible`：存在明确冲突并引用原文。
- `unknown`：关键信息不足，需要用户或岗位补充。

任何明确硬性冲突都不能被语义相似度或 AI 判断覆盖。

### 4.2 第二阶段：证据召回与覆盖

目标是找出岗位要求和简历证据之间可能存在的对应关系：

1. 规范化技能和岗位词典进行精确匹配。
2. 同义词、别名和可迁移能力规则召回。
3. 语义检索召回相近证据。
4. 对候选对应关系进行重新排序和人工可解释校验。

对学生需要额外识别：

- 课程设计和实验。
- 个人项目和开源贡献。
- 校园组织、竞赛和志愿服务。
- 内容作品、调研、咨询和用户沟通。

这些经历可以证明能力，但不能被包装成正式工作经验。

### 4.3 第三阶段：AI 解释

AI 只接收已经结构化的岗位要求、候选证据和规则判断，生成：

- 为什么值得或不值得投递。
- 哪些要求有证据支持。
- 哪些要求只有弱证据或没有证据。
- 哪些信息仍然未知。
- 简历应该优先展示哪段真实经历。
- 投递前可以完成的准备动作。

AI 输出必须符合固定 JSON Schema，引用 `requirement_id` 和 `evidence_id`。不能引用不存在的经历，也不能修改硬条件结论。

## 5. 推荐结果

前台使用推荐等级，不把单一百分比分数作为主要结论：

| 等级 | 含义 |
|---|---|
| 优先考虑 | 无已知硬性冲突，核心要求有较强证据支持 |
| 有条件考虑 | 无明确硬性冲突，但存在可见缺口或重要未知项 |
| 不建议 | 存在明确硬性冲突，或核心要求长期无法满足 |
| 信息不足 | 岗位或用户信息不足，不能可靠判断 |

可以保留内部排序分，但必须拆成独立信号：

- 资格状态。
- 核心要求证据覆盖。
- 次要要求证据覆盖。
- 用户偏好契合。
- 信息完整度。
- 结论置信度。

这些信号不能被压缩成一个看似精确却无法解释的数字。

## 6. 输出契约

每个推荐结果至少包含：

```json
{
  "recommendation": "conditional",
  "eligibility": "eligible",
  "supported_requirements": [
    {"requirement_id": "R1", "evidence_ids": ["E3"], "strength": "strong"}
  ],
  "gaps": [
    {"requirement_id": "R4", "gap_type": "missing_evidence"}
  ],
  "unknowns": ["每周出勤要求未写明"],
  "summary": "...",
  "next_actions": ["..."],
  "confidence": "medium"
}
```

前台允许用户展开查看原始岗位句子和简历证据，形成可核对的解释链。

## 7. 隐私与模型边界

- 简历解析与岗位采集使用不同的服务和权限。
- 模型请求只发送完成任务所需的最少字段。
- 不在提示词、日志或错误信息中包含联系方式等无关个人信息。
- 第三方模型不可用时，硬条件和基础规则匹配仍然工作。
- 抓取到的岗位内容视为不可信数据，不能改变系统指令或获得工具权限。
- 用户删除简历时，同步删除原文、解析结果、向量和模型缓存。

## 8. 评估方法

### 8.1 固定测试集

建立经过人工标注的岗位和简历测试集，至少覆盖：

- 明确符合和明确不符合。
- 毕业年份、学历和实习时长冲突。
- 同义技能和可迁移能力。
- 信息缺失。
- 学生项目证据。
- 岗位描述中的提示注入文本。

### 8.2 指标

- 硬条件冲突漏检率。
- 要求提取准确率。
- 证据引用正确率。
- 不存在证据的幻觉率。
- Top-N 推荐人工相关性。
- 用户认为“推荐理由有帮助”的比例。

匹配模型或提示词升级前必须回归同一测试集，不能只凭几个演示样例判断变好。

## 9. 人在环

用户对解析结果拥有最终确认权。系统必须允许用户：

- 修改错误字段。
- 拒绝系统推断的技能。
- 标记自己实际不想投的岗位。
- 反馈某条推荐理由不成立。

这些反馈用于修正规则和评估，不直接把用户的一次操作当成普遍规律。
