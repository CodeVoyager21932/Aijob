# Aijob 产品体验审视：从第一份简历到能解释自己的经历

## 结论

当前项目已经具备岗位、材料、申请、面试和准备任务的工程骨架，但主要交互仍然围绕数据确认、版本固定和对象关联展开。新手需要先理解系统的组织方式，才能得到一份可用简历；有经验的使用者也要承担许多重复操作。面试的问题选择和反馈质量则有已经复现的实质缺陷。

下一轮应优先改善**完整经历的整理、第一份简历的起步、岗位相关追问和答后修改**。增加菜单数量不能解决这些问题。现有事实追溯、历史投递稿和权限边界应继续作为底层能力，在用户有需要时展示。

“经历提炼”和“模拟面试”适合共用同一份完整经历，但应保留两个目的：前者帮助用户发现并写清真实贡献；后者检验是否回答题意、理解方法和取舍、能否解释自己的表述。面试还涉及岗位理解、动机、情境处理和反问，不能全部归结为简历润色。

## 从第一次写简历的学生出发

### 我需要的是起点，系统先要求我交一份简历

空材料页的主入口是“解析并确认简历”。一个尚无简历的学生只会看到上传文件或粘贴正文；新建复用材料虽然允许空白输入，也只提供名称、用途和正文，没有帮助他回忆可写的经历。

学生此刻可能连“课程作业能不能写”“只负责一小部分算不算”“没有阅读量怎么办”都不清楚。空白输入框、完整度提示和专业术语无法代替帮助。

建议提供三个直接入口：**从零写第一份简历、导入已有简历、围绕一个岗位准备**。可以用社团、课程、实验室、实习、个人作品等真实场景引导回忆；熟练用户可直接粘贴或编辑，不强制做问答教程。

### 我刚确认过，又被要求初始化、关联和再确认

本轮用一条教育信息和两段校园/课程经历，得到 8 个独立候选勾选项，其中项目名称也单独算一项。确认保存后，没有立即进入可编辑简历，还要点击“初始化为可编辑简历”。初始化后的原样区块又显示“0 条证据”，旁边列出刚确认过的那批内容供关联。

这些行为在数据库中分别有用途，但对用户看起来是重复劳动：同一份内容已经确认，为什么还要再证明它来自哪里？机械拆分还允许只选中结果、漏掉责任边界，或只选动作、丢掉结果。

建议以完整经历为主对象。用户可以整段接受、修改项目归属，系统在后台保留句子依据；只有新增或不确定的事实需要特别核对。保存成功直接进入可编辑产物，迁移/初始化由同一个用户动作完成。

### 我来写东西，首屏却一直在解释系统

桌面编辑区同时存在全局侧栏、简历资产列表、章节结构、正文、证据和建议等区域。手机上这些区域大量纵向堆叠。本轮 360px 样例中，第一个简历正文输入框起点约为 1871px；已有一次回答的面试页面，下一题输入框起点约为 2319px。800px 高度的首屏尚未到实际写作位置。

测量没有发现这些页面的整页横向溢出，问题集中在主任务被辅助内容推远。面试页甚至先给“删除求职项目”、阶段条、版本条、介绍卡、规则说明，再给题目。

建议进入编辑就看到正文，进入练习就看到当前问题。历史、目录和依据用抽屉或折叠面板；移动端不把桌面所有栏依次铺开。

### 我需要知道“做什么”，而不只知道“还缺什么”

图谱已经能从统计进入岗位原句，这是有价值的基础。但“Excel”“沟通协作”等标签不能直接告诉新手应练到什么程度。全部职能混在一起时，常见词也不等于他申请的方向最值得准备的能力。

建议从岗位任务解释能力，例如“把重复反馈归类，说明分类依据，并形成可阅读的汇总”，再给一个适量、可跳过的准备动作。已有经历应优先复用；没有相应产物时给练习建议，不能把做练习自动登记为真实工作经历。

## 从善于选人、也愿意指导的面试官出发

### 我关心的是贡献边界与判断过程

“使用 Excel”“参与运营”只能提供线索。值得追问的是：遇到什么问题、你具体承担哪一部分、为何这样处理、结果能说明到什么程度、有哪些限制。把动作、结果、项目背景散成平级句子，会削弱这些关系。

对经验单薄的学生，能诚实说明一件小事的分工和判断，通常比堆砌宏大的词更值得继续了解。这是本报告采用的评审标准，不能由此推算真实录用概率。

“做过”写成“做成了”需要保留边界。没有流量后台，就不添加增长率；共同讨论的结论不能写成独立洞察；失败实验、未上线的课程项目也可能展示方法和反思，不强制包装成商业成功。

### 当前面试的选题存在明显错位

实际创建一个仍处于“感兴趣”的岗位项目，建立岗位简历后，可以开始面试，**技术上没有“必须已投递”的阶段限制**。但开始前若缺少岗位简历，页面先给可点按钮，点击后才报 409，要求返回创建简历。

更严重的是，本轮第一题引用“宝安区”，要求用真实经历解释做过什么；同时引用“某大学 本科 在读……”追问个人职责、方法与产物。

代码只过滤部分未知/其他要求，取前 3 项；简历引用直接取第一段。因此工作地点可能变成行为面试题，教育信息可能被当成项目经历。下一题还会将上一回答的追问与另一条岗位问题拼在一起，让用户同时回答两件事。

### 当前反馈能检查格式信号，不能可靠识别空洞表达

直接调用现有 `buildDeterministicInterviewReview`，使用相同结构、无外部模型的合成输入，得到：

| 输入 | 当前结果 | 说明 |
|---|---|---|
| 115 字套话，包含“背景、目标、负责、行动、最终、结果”等词，但无具体任务或产物 | 没有表达提示；优点中说达到 80 字、提供更多可见细节 | 结构词和长度可以通过检查，不能代表内容具体 |
| 62 字，回答四人问卷作业里自己的分类和画图分工 | 被提示太短、缺完整情境任务行动结果 | 针对窄问题的具体回答被要求扩写成完整故事 |
| 26 字，直接说明到岗日期、每周天数和持续时间 | 同样被提示太短、缺完整链条 | 事实问题不应套用行为经历结构；此项是函数适用范围探针，不声称当前问题生成器会原样提出该问题 |

当前界面明确说明是确定性模板，这一点应肯定。但本轮已证明，它还不足以支撑“检验表达空洞、逻辑不稳”的宣传承诺。不能通过换成“专业面试官”标题掩盖能力差距。

反馈应依据题型，指出原回答哪句话有问题、缺少哪一处信息、为什么需要补充；一次优先解决一个问题。对于不知道或没有参与的部分，应允许直接说明。

## 这两个环节怎样融入产品

建议保留“机会、申请、材料”主导航。材料中以“我的经历、简历、常用材料”组织；面试既可从一段经历快速进入，也可在同一岗位申请中继续。一次短练习不要求用户先建立完整申请档案。

```mermaid
flowchart LR
  A[回忆或导入一段完整经历] --> B[补充个人动作与已知结果]
  B --> C[生成并编辑简历段落]
  C --> D[围绕这段经历或目标岗位练习]
  D --> E[定位一个表达或内容缺口]
  E --> B
  C --> F[准备投递稿并记录实际提交版本]
  F --> D
  E --> G[加入一个具体准备动作]
```

这是一条可往返的路径，用户可跳过不需要的环节，不是必须全部完成的关卡。

### 经历提炼：先让用户想起来，再让表达更准确

初始只问一件事：“最近做过哪件能说出具体过程的事情？”提供课程/社团/研究/实习/个人作品的例子，也允许直接粘贴。

随后根据已知内容只追问缺失且有价值的信息。例如：“你说参与问卷，28 份回答中具体哪部分由你处理？”“你如何处理重复分类？”“结果由谁使用？”每次一问，允许“没有”“不记得”“不由我负责”。无目标岗位时照样整理经历，有目标时才优先提取与任务有关的内容。

产物是完整经历卡与可编辑段落，而不是一串待勾选技能。卡片可以展开看背景、个人分工、方法、结果/限制及依据，不强制每段写成四个 STAR 标题。

本轮虚构样例可以整理为：

> 在四人课程小组中，整理 28 份二手书需求问卷，将重复表述合并分类并用 Excel 绘图，参与课堂汇报；项目停留在课程研究阶段，未上线交易平台。

这段话只使用已提供的信息。若要进一步突出取舍、结论或成效，应继续询问事实，不能自动补上转化率、上线成果或“独立主导”。对读书会样例可以保留“协助发布 12 篇推文”，阅读量未知也能正常完成整理。

### 面试练习：从讲述进入检验

提供两个简单模式：

- **边练边指导**：适合第一次准备的人；针对一段经历，回答后给一项反馈，再试一次。
- **模拟一轮**：围绕目标岗位连续提问，主要反馈放到结束后；过程中可以追问，但不每句打断讲课。

选题按岗位任务、简历重要主张和用户希望练的点确定；招聘资格用短问短答，经历题问责任、方法和取舍，情境题检查分析过程，研究题关注方法与局限。面试应覆盖岗位理解、动机及合理反问，避免所有问题都变成“请再讲一遍简历”。

一条有用反馈应包含：原回答片段、具体问题、建议补充的信息、下一次尝试。例如：“你说‘我们完成了分析’，我还无法分清你的贡献。请只补充你负责的输入、处理过程和交给谁使用。”不要先给漂亮的整段答案，让新手背诵不属于自己的故事。

记录当前稿/实际投递稿的上下文，允许在二者之间明确选择。面试回答是练习记录；只有用户采纳的事实变化才能进入材料。练习中的假设方案、系统示例和准备计划不能混入经历事实。

本轮可以继续使用文字练习来训练内容组织。它不能据此判断发音、语速、停顿和真实口语表现。“说得清”若用于产品介绍，应说明当前具体支持的训练方式；录音和语音评价保持后续范围，不作为这次改好主流程的前置条件。

### 同一事实可以有多种表达，不产生多份互相矛盾的经历

底层建议在现有结构上增量扩展：完整经历保留自己的标识和确认修订，内部语义片段指向所属经历和原句；简历短版、面试讲述稿、材料片段引用这一来源，并保存各自用途。已有历史 Case 和实际投递正文继续保持原版，不由后台重新解释覆盖。

拆句数量不应变成能力强度：同一项目换成十个短句，不应获得十份独立经历的权重；同一技能在多处重复，也不等于熟练程度提高。本轮没有测得“拆得越多，系统就给出更高适配度”的结果，不能把这种可能性当成已证实缺陷。需要验证的是项目归属、语义去重、任务深度和结果边界是否保留。

导入文件的临时保存策略、用户确认的完整经历长期保存、向外部 AI 发送的裁剪内容，是三种不同问题。保留原始上传文件与否需要单独的明确产品决定；本报告没有修改当前原文删除策略。可以在不保留上传文件的前提下，保住用户已确认的完整经历和上下文。

## 隐私如何服务体验

隐私处理对求职者有实际价值：经历、联系方式和未公开项目不应被任意公开或传播。但正常流程的主要任务应是写作、选择和准备。系统自动执行的保护措施不需要每次都变成用户的阅读作业。

建议首次导入用一小段可展开说明；正常状态不使用警报样式。真正调用外部 AI 时，让用户知道会发送什么，并可查看内容；日常编辑只显示保存状态。删除全部资料仍保留清楚的不可逆确认，普通保存不套用同样的仪式。

最终投递简历需要适当的联系方式，AI 输入应做最小化处理。两者的用途不同，不能把去标识化占位符直接当成可投递稿。此项是必须补验的出口场景，本轮虚构样例没有联系方式，未声称已复现导出缺联系方式的问题。

这种默认聚焦主任务、按需展开细节的安排与 [NN/g 的渐进展示原则](https://www.nngroup.com/articles/progressive-disclosure/)一致；它不等于让用户经历更多强制步骤。

## 网上经验怎样进入产品

用户后续提供的材料应先转成小型指导条目，记录来源、发布时间、适用对象、适用岗位/题型、具体建议、例子和不适用情况。官方招聘要求、求职指导文章、社区个人经验、用户自己的事实分别保存，不能互相当作证明。

例子：“不要只写负责什么”应出现在用户写“负责新媒体运营”之后，帮助补充动作和成果；“说清个人分工”应出现在多人项目回答中；不能把整篇文章塞进模型上下文后要求所有用户照做。

国家大学生就业服务平台刊载的人社部 [简历准备指导](https://xn--dj-gt9c.ncss.cn/ncss/zd/jl/202411/20241118/2293345457.html)强调面向岗位选择经历、说明个人任务与行动，同时只提供求职所需信息。这支持保留完整经历并选择相关表达；**不构成拆成独立勾选句、每条必须有增长数据或反复确认隐私的依据**。

建议优先吸收四类指导：没有实习如何整理课程/研究经历、团队贡献如何界定、结果不明如何诚实表达、如何针对具体追问回答。暂缓百科式课程体系、经验社区和大量静态题库，避免又增加一个与写作脱节的系统。

## 建议实施顺序

1. **修正现有错误并减去重复步骤。** 修复问题选择/反馈类型、地点核对、初始化和重复引用；精简主流程文案和首屏。先得到一个不出明显荒谬题、可以直接编辑的现有流程。
2. **补齐“从零整理一段经历→首份简历”。** 增加完整经历对象及纠错归属，复用当前编辑器与导出；同时保留熟练用户直接编辑入口。允许无数据、非商业成果、多人协作和失败经历。
3. **把岗位表达与练习连成往返。** 经历卡/简历段落可直接开练，题型选择、一次追问、针对回答的反馈、重答对照和建议采纳都回到同一上下文；基础规则在 AI 不可用时提供诚实、有限但相关的自检。
4. **把指导内容、准备动作和日常使用接通。** 指导卡出现在卡点，练习结果可创建一项具体准备事项；精简移动端，补齐身份保存与真实运行配置，继续既有性能/发布验收。

每批完成可用产物再推进。保留原计划的数据、采集、历史兼容和权限边界，把产品主体体验的质量标准提高；不通过新增候选功能无限延迟首发，也不把已通过工程测试解释成用户体验成熟。

## 下轮验收用的代表性任务

- 首次写简历：无文件、无目标岗位，只给两句校园经历，也能留下第一份可编辑稿；无需理解 Case、证据 ID 和修订编号。
- 成熟用户：导入已有 STAR 项目，项目整体不丢；直接调整段落和版式，不被强制拉回逐句勾选。
- 经历单薄：不提供编造的业务数字也能完成；“没有”“不归我负责”“记不清”有正常分支。
- 硕博研究：失败实验或阶段结果可以展示方法、个人贡献及局限，不强制写成增长故事。
- 关键反例：地点不生成项目题；教育标题不被当成经历；套话不被判具体；资格短答不被要求 STAR。
- 投递前练习：无已投递记录也能练一段/练岗位；一次只回答一个问题，能够重答并看见具体改进。
- 回写：面试假设和模型示例不成为个人事实；采纳后的材料变化可检查，历史实际投递稿保持原样。
- 日常使用：中途离开可恢复，保存状态明确；320/360px、200% 缩放、键盘及焦点恢复另做完整验收。
- 反馈收集随交付进行：记录完成首段的耗时、重复确认次数、迷路跳转、首次练习启动成功、追问相关性和改写后能否解释；不把没有真实用户数据的目标值标成达成。
