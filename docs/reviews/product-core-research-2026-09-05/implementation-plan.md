# 产品主体改进实施顺序

研究于2026-09-05开始，2026-09-06整理。状态：研究建议，业务实现尚未开始。依据为[主报告](report.md)、[中文资料与技术证据](sources.md)和[代码复现](audit-results.json)。

## 1. 首先交付什么

第一条完整体验：**一个没有上传简历的学生，也能找到值得考虑的岗位方向，看懂这一组岗位在做什么、要求什么，追溯具体原句，再把已有经历或一个准备动作带入申请。**

保留官方事实、Case、材料与投递闭环；改进用户进入这些能力的路径。OS-7、事实纠偏、取消公司上限、业务恢复继续有效。本计划不要求重做这些工作，不要求等待固定人数研究后才开发。

这五个切片是依赖顺序，不是五个等量大版本。第一轮核心范围包括下面A及C的基本体验、B中已有厂商的自动化、D中最基础的材料与时间管理。完整职业百科、多行业精细词表、全部ATS接入、自动生成成长课程、复杂通知和Offer分析都不阻塞首发。

## 2. 切片A：先让系统正确理解，再让用户看懂

**用户变化：** 硕博不会在公开目录中被统一排除；“不限985”不会被误判为院校限制；AI产品等交叉岗位可正常检索；小样本仍能展示明确事实。

| 层 | 修改范围 |
|---|---|
| 产品契约 | 明确学历/毕业窗口、否定/优先/必要性、多个合理方向标签；官方事实和系统分析分开；小样本仅作样本描述 |
| Contracts | 修订`packages/contracts/src/job-reachability.ts`及洞察返回契约，保留原句、语义状态、统计分母和缺失情况；移除用硕博身份作全局排除的旧逻辑 |
| 数据库 | 核对迁移037中的同名可投谓词和所有查询消费者；新增迁移更新当前投影，不改旧迁移或既有不可变版本；旧Case要求集不被后台升级 |
| Platform | 调整`job-family-classifier.ts`，支持主职能与领域标签；调整`insights/service.ts`使“被提及”和“是否硬性”独立，小样本不返回空白占位；过滤尽可能下推SQL |
| Web | 用现有机会和洞察页面承接“看方向/看岗位”切换；隐藏运行ID等主流程术语；展示样本范围、原句入口和下一步；保留旧链接兼容 |

先整理代表性语料，再实现规则。语料包含明确必需、优先、否定、或条件、职责与资格混写、学历/月份窗口、混合岗位、缺失字段，以及产品/运营/技术/研究/制造/法务等例子。本轮合成例子是起点，不充当人工金标。真实官方例句只能来自已有合规本地材料或获准采集。

**完成依据：**

- “本科及以上，不限985、211”与“985院校优先”都不会触发院校硬性排除；明确限制仍可见且准确解释，不暗中替学生筛掉。
- 硕士/博士岗位在范围、目录、Case创建/升级、匹配、洞察各消费者中一致；SQL与TypeScript结果对齐。
- 同一岗位多地点不重复计数；19岗/5公司及20岗/4公司的原句可查看；必要性未知不冒充必需，也不会让已提及内容消失。
- 没有简历可完成浏览、查看原句和收藏；用户未声明的条件保持未知。
- 新增PostgreSQL集成验证覆盖公开资格和旧Case固定版本；再运行相称的lint、typecheck、测试与build，不触碰业务库做测试。

**边界记录：** 本硕博范围来自coco已确认需求，记录新ADR即可，不再重复征求这一范围。否定和优先的纠错属于忠实性修复。语义分类能否参与公开资格、未知分类如何展示需在契约中明确，不能顺手降低来源准入。

## 3. 切片B：让供给自动流转，人工处理例外

**用户/运营变化：** 正常更新自动出现，异常不会让全站停摆；接入同厂商新企业时复用已有能力，只处理企业身份与新访问范围。

先从当前北森与已有自建API适配器做完整链路，不先接十个新厂商。来源排序同时看学生需求覆盖、接入成本、稳定性和可用权限；不能仅按招聘量，也不能限制大公司岗位数。

| 层 | 修改范围 |
|---|---|
| 契约 | 分离发现状态、主体证据、访问范围、技术能力、公开资格、运营健康；状态变化带原因与证据版本 |
| 数据 | 优先复用现有source/evidence/task模型；增加一次完整列表轮次的完成标记、解析版本与证据内容哈希；只有缺少可表达字段时新增表 |
| 采集 | 扩展现有厂商识别/租户配置草稿；列表优先、必要详情、条件请求、幂等去重；证据内容变更才触发复核 |
| 调度 | 每主机/租户预算、来源局部熔断、429退避、队列积压观测；提升容量须有请求预算验证，不能只修改每小时来源数 |
| 内部操作 | 第一版用CLI生成可读的异常报告和批量处理草稿；随后按实际运营需要加内部界面，执行仍复用同一服务层 |

**完成依据：** 相同批次重复执行不产生新语义版本；分页失败不会批量下架；无变化来源不反复进入人工队列；租户A故障不阻塞无关主机B；来源暂停/权限撤销及时撤回目录与聚合；记录每新增企业与每百次普通刷新实际需要的人工步骤和时间。

**需要单独决策的扩展：** robots资源缺失的细分处理、受控生产浏览器渲染、内部运营UI。它们是可评估选项，不是本轮已经启用的能力。公开接口文档不能代替API凭据或企业许可。新网络范围仍需明确启用。

## 4. 切片C：从共性要求走到自己的准备

**用户变化：** 用户能比较方向差别，选中一项要求，看到它在哪些岗位出现、对应哪些已有经历，再决定补充哪项真实材料。

第一版选择有实际供给的少量子方向展示，体系支持其他职能扩展。不将无数据的方向写成已经覆盖，也不因为首批数据偏技术而把产品定位改为程序员求职站。

- **语义层：** 稳定概念ID、别名、主职能/子岗位/领域/任务、必要性和原句引用。规则提取保底；模型只补充解释层，记录版本、成本和不确定性，冲突时不覆写官方事实。
- **统计层：** 岗位提及数/全部岗位数、企业提及数/全部企业数、解析覆盖、核验时间范围。每岗位每概念去重，未提及不等于不需要；不把来源增加误称市场升温。
- **查询层：** 规范化筛选参数；公共统计按数据版本、准入版本、提取版本复用；个人经历对照独立计算。公开权限变化使缓存失效。第一版先做正确SQL与按需缓存，数据量小不抢建复杂增量系统。
- **体验层：** 条形图点击到原句与岗位；对比两个方向时显示相同口径；从收藏集合选择准备优先项；有材料时先补解释，避免把每一项都变成新课程。
- **材料层：** 尽量复用现有证据/材料模型；准备任务与事实分开。勾选“准备完成”不自动把技能写进简历；用户确认产物内容后才能变成职业资产。

**完成依据：** 同一要求跨岗位累计一次/岗，公司无截断；新用户不用触发“运行”即可看到概览；两用户共享统计但无法访问彼此经历；撤销来源后不能从旧缓存看到撤回的公开原句；准备产物能回到已有材料并用于一个真实的Case流程。

[交互示意](role-map.html)只用于评审上述连接和统计表达，不是生产UI或真实市场数据。第一版不做趋势预测、全行业知识图谱、能力打分排行榜。

## 5. 切片D：把频繁、琐碎的投递工作做好

**用户变化：** 常用内容不用重写，面试前能找到实际投递稿，今天到期的事情不会被最近编辑的申请挤掉。

依高频顺序逐项交付，每一项都能独立使用：

1. **投递稿与常用材料：** 在现有基础简历/岗位简历上增加轻量方向复用和实际投递版本关联；提供自我介绍、项目长短版、邮件草稿、命名与逐段复制。复用现有DOCX能力并增加可验证的PDF输出。
2. **时间与批量进度：** 复用既有Case状态、事件与截止日期；增加笔试/面试/待跟进记录、今日排序、批量修改和ICS导出。内部提醒需去重、时区、关闭与已完成语义；暂不强制接入邮箱。
3. **招聘计划：** 企业级招聘季、毕业月份范围、志愿次数、修改规则、适用年份与证据版本；岗位引用计划。规则冲突显示待核实，不自动替用户判无资格。

**完成依据：** 后改的简历不会替代已投递稿；PDF中文、分页、链接、文本可复制并与预览一致；明天截止优先于远期新修改；不回复不会被推断拒绝；同一提醒不会重复轰炸；批量操作支持部分失败反馈；企业规则不跨招聘季自动继承。

PDF渲染工具与依赖需先检查运行成本及文件隔离；方向稿先尝试用现有简历文档派生关系表达，避免创造三套编辑器。Offer比较可晚于这些基础工作。

## 6. 切片E：面试连续性、性能与发布衔接

围绕用户实际投递稿、岗位原句和先前回答做追问与复盘，复盘产物回到材料/下次准备。文字模式先做好；语音、视频评分、面部表情判断不列为本轮建设目标。没有模型时提供有用的岗位问题与结构化自检，不假称完成了真人水平面试。

性能工作穿插于A–D，不等到最后才设计索引。E集中检查完整旅程和混合负载：目录/图谱读取、Case写入、解析/导出后台任务、来源刷新。用1万/10万合成岗位和20/50/100并发请求测容量曲线，不将1000累计用户偷换成1000并发。

建议起点为热读取p95≤500ms、首个有用方向概览≤2秒；记录部署资源、数据分布、冷/热状态、错误率与队列延迟后再调整。优先修正实测热点；不预设Redis、向量库或微服务。

完成这条核心旅程后，按实际开放功能补齐账号、数据恢复、邮件、模型供应商及公开来源等发布事项。它们没有被取消，但不再作为当前产品主体研究的替代品。
