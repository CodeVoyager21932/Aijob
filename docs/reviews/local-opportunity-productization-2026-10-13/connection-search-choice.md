# 一套还是两套配置：从用户视角修订搜索连接设计

日期：2026-10-13。本文是对主报告第 5 节的设计修订，尚未实施。依据 coco 的反馈：尽量减少配置，允许选择使用模型平台的搜索或独立搜索，并由产品帮助判断接口能力。

## 结论

**不强制两把 Key。提供一个连接入口，按实际能力复用，缺少搜索能力时再给选择。**

之前把“模型负责理解、搜索负责发现”的内部职责，过早对应成了两套用户配置。职责需要区分，用户不一定需要两个账户或两个 Key。已经有服务把模型调用和联网搜索放在同一平台、同一认证下，Aijob 应支持这条路径。

切换的是“新网站发现使用哪种搜索方式”，不是“大模型/搜索”互斥总开关。写简历继续使用选定的模型；既有官网刷新、岗位变化摘要和手动简历都不应依赖外部 Key。

## 1. 当前事实与可行性

| 情况 | 能否减少成一套连接 | 必须明确的条件 |
|---|---|---|
| 模型平台提供可调用的搜索工具 | 可以，用同一连接承担写作和搜索 | Aijob 适配对应接口，当前账号/模型获准使用，能读取真实搜索来源 |
| 平台在模型之外提供同账号搜索 API | 可能仍只填一次 Key | 两项认证范围确实一致；搜索入口由产品适配，不让用户重复配置 |
| 只有普通文本生成 API | 不能靠开关赋予联网能力 | 可保留它写作，另配搜索；也可换成带搜索的平台，或暂不开新网站发现 |
| 不配任何外部连接 | 已启用官网照常刷新 | 不能把它说成已经在全网寻找新网站 |

当前官方文档的具体依据：

- **OpenAI** 的 Responses API 提供 `web_search` 和结构化来源信息，说明同一平台连接可以同时用于模型与搜索，具体支持取决于所用模型/端点。[官方文档](https://developers.openai.com/api/docs/guides/tools-web-search)
- **阿里云百炼** 提供联网搜索；不同协议启用方式和来源返回能力有差异。Chat Completions 可用 `enable_search`，但其部分来源字段不在该兼容路径返回；Responses 或原生接口可提供搜索来源。不能只加一个参数就声称已适合岗位发现。[官方文档](https://help.aliyun.com/zh/model-studio/web-search/)
- **OpenRouter** 当前提供 `openrouter:web_search` 服务端工具，沿用 OpenRouter 认证，能够选取平台提供的搜索引擎。它仍有搜索及模型费用；一把 Key 不等于免费。旧 `web` 插件和 `:online` 路线在当前文档中已标为 deprecated，新适配不应照旧教程实现。[官方文档](https://openrouter.ai/docs/guides/features/server-tools/web-search)
- **DeepSeek** 不能笼统判定“没有搜索”。官方明确在 Claude Code 接入方式中提供 Web Search，并产生额外模型请求费用；但这不能证明任意中转站的 Chat Completions 端点也支持该能力。该接入方式是否适合作为 Aijob 的稳定调用契约，仍需专门适配，不要求普通用户安装 Claude Code。[官方接入说明](https://api-docs.deepseek.com/quick_start/agent_integrations/claude_code/#using-web-search-in-claude-code)

这些是官方文档能力，不是对 coco 当前中转账户的真实搜索测试。本轮没有访问密钥或发起收费验证。

## 2. 推荐交互：默认帮忙判断，始终可以稍后处理

第一屏只做“连接你的 AI 服务”，保留已有地址、Key、模型。没有 AI 的用户可直接跳过，使用已接入岗位。

选择“寻找更多招聘网站”后，界面给出：

| 选择 | 展示方式 | 后果 |
|---|---|---|
| **使用当前 AI 服务联网** | 当前连接具备已验证能力时推荐；未检查则同一操作内检查 | 不填第二把 Key，费用计入该平台 |
| **使用独立搜索服务** | 可主动选择；当前连接不支持时提供，首版沿用 Tavily | 保留原模型，另配一个搜索连接 |
| **暂时只更新已接入官网** | 始终可选，不显示为配置失败 | 不探索新网站，已有来源及摘要继续运行 |

如果已有可用配置，默认沿用。不能因为上线单连接模式，就自动把 coco 当前已工作的 Tavily 切走；仅在用户选择新方式后变更。停用不删除 Key，日后可以切回。

对于第一次配置的新用户，默认先看当前 AI 连接是否可用于搜索，成功便推荐复用。若用户只是要找岗位而没有模型，也应能直接配置搜索，无须先购买模型接口。

联网能力检查应合并在“保存并检查”或第一次启用发现的操作内，并简短说明会发起一次供应商可能计费的小请求。不做额外多轮确认，不让检查成为使用基础功能的门槛。协议、工具名、JSON 格式和搜索参数由产品处理。

## 3. 能力识别要分层，不能假装识别所有中转

**先识别，再在必要时验证：**

1. 从已知服务地址、明确的供应商预设和能力信息选择适配方式。`/models` 只能辅助选模型，不能单独证明联网。
2. 首次启用该连接的搜索时，执行一次短搜索请求，读取供应商定义的工具执行结果、来源元数据及可解析 URL。只向用户配置的服务地址发送其 Key，不把中转 Key 试发到其他平台。
3. 成功记录具体连接、模型、接口方式、适配版本和验证时间；配置未改变时不反复测试。
4. 运行中通过正常请求更新状态。一次成功代表本次能力可用，不等于之后所有请求、所有招聘网站都可用。

不能以“模型说自己能联网”“回答写了几个链接”“知道今天日期”“HTTP 200”认定成功。中转可能忽略不认识的参数，网页端的搜索按钮也不等于 API 暴露了搜索。

对用户只需显示四种结果：

- **联网可用：**可使用这套连接继续寻找网站。
- **当前调用方式不支持：**提供换连接、独立搜索、稍后配置。
- **尚未识别：**Aijob 暂未适配或资料不足，不能直接断言该平台不支持；允许查看平台说明、选择已有兼容方式。
- **暂时无法检查：**网络、余额、认证或权限问题，明确具体原因并保留配置。

“会联网回答”和“适合自动发现网站”也要分开：若接口只给一段综合回答，没有可提取的来源，仍可用于普通问答，但暂不能可靠替代来源发现接口。不让模型补造岗位列表完成这个缺口。

## 4. 用户选择权不只是下拉框

- **少配一次：**已有连接能兼任时复用；无法兼任才按需展开第二套配置。
- **少学概念：**展示用途和可用结果，不要求用户先懂 API 协议。
- **可以不用：**不配模型仍可找已有岗位，独立搜索也不强制模型；不配搜索仍可写简历和更新已有官网。
- **可以切换：**搜索方式与写作模型各自选择，保存配置，切换不丢方向或结果。
- **费用可预期：**搜索可能另外计费或消耗模型 Token；启用时说明预算。失败时不默认切换另一家供应商，只有用户事先选择备用方式才使用。
- **不制造隐藏工作：**同一 Key 的复用只在明确选定用途和预算内生效。选了写作不自动允许后台搜索，选了本人方向搜索也不允许全局替其他用户消耗。

当前 PG 发现任务是 ownerless，不能直接把个人 Key 塞入该全局配置。后续实现需让连接用途、所有者、预算与对应订阅关联；执行位置仍保留三个服务边界，凭据不因此共享或越权。

计费也不能沿用“一个 HTTP 请求永远等于一次搜索”的假设。有的平台一次生成会执行多次搜索工具，适配器应限制调用次数和输出，分别记录外部请求、搜索工具及模型消耗；拿不到精确费用时明确是预算估算。Tavily 既有尝试计数继续保留。

## 5. 对 Aijob 的最小改动方向

当前 [模型 provider](../../../apps/platform/src/ai/provider.ts) 只发送普通 Chat Completions 结构化生成请求，不发送搜索工具，且拒绝 `tool_calls` 响应；[发现模块](../../../apps/platform/src/opportunities/discovery.ts) 当前明确调用 Tavily。因此“一套 Key 自动联网”是新增适配能力，不能只改设置文案或加一个未生效开关。

建议增量限定为：

1. 保留现有个人模型连接，将“搜索方式/连接引用/用途预算”独立表达；统一用户入口，避免复制同一秘密。
2. 保留 Tavily 适配器；增加已核实文档与用户实际服务相符的同平台搜索适配器。不要一次铺开十几家供应商。
3. 各搜索适配统一输出线索 URL、标题、来源与必要使用状态，后续仍走原来的官网核验、接入和 collector。
4. 用一次真实搜索和相关响应夹具确认调用没有被忽略、来源可读取；不重复测试未改的聊天连接，也不做所有模型矩阵。

可接受的产品承诺是：**优先一套配置，系统帮助确认能力，用户随时选择独立搜索或仅更新已有来源。** 不承诺任意 Key 都能联网，不强制所有用户再注册搜索平台，也不取消岗位事实核验与来源维护。
