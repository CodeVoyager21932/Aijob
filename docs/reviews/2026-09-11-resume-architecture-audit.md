**结论**

当前问题确实跨越简历模块的底层边界，不能归结为字号、颜色、一个解析正则或某一套模板。它由五个相互放大的缺口组成：

1. 导入先丢掉文档结构，再用依赖结构的规则识别，未识别的整份简历仍被标记成功。
2. 内容字段的含义在导入、表单、材料和模板之间不一致；系统能保存文字，却不能稳定保存“这所学校、这段实习、这项成果”的关系。
3. 模板适配保留了部分外观，但没有完整承接上游的模块结构、字段编排、区域和排版规则。统一渲染器过早压平了模板差异。
4. 编辑器把大量底层操作直接排成连续表单，缺少整理错误结构的能力；预览能装下一页，却不适合持续阅读和对照。
5. 验收主要证明文件和文字可以流转，没有充分证明真实简历能够被正确理解、顺畅编辑，并获得成熟的排版。

因此，当前准确状态应是：**已有可复用的保存、版本、附件和导出工程基础；简历的导入理解、模板还原和实际编辑体验尚未达到成熟产品标准。** 不能继续表述为“主体完成，只剩小细节和真实配置”。上一轮把有限工程验收外推为核心质量完成，判断过度，需要纠正。

**一、已经复现的导入失败链**

```text
PDF 的文字片段、坐标和换行
    ↓ 只取 str，并用空格连接
每页变成一行长文字
    ↓ 模块识别却要求独立标题行
一个 custom 模块「导入内容」
    ├─ 表单通用标签显示为「工作内容与成果」
    ├─ 模板收到一个长正文，无法生成教育／项目的层级
    ├─ 经历自动收录不接收 custom
    └─ 导出能完整输出这段文字，仍可能通过文字完整性检查
```

数据库只读检查还发现：当前 `profile.resume_originals` 可见的 5 条 PDF 导入均为 `succeeded`，对应草稿均为 1 个 `custom` 模块、1 条记录。这些记录可能包含既有验收操作，因此不能将 5/5 当作市场解析准确率；它证明当前运行结果与“成功”的定义确实脱节。

**I-01｜严重：解析层主动丢弃下一层需要的证据。** `resume-parser-child.js:159–168` 只提取 `str`，丢掉 PDF 的 `hasEOL`、坐标、宽高和字体信息。`studio-content.ts:141` 开始的识别却依赖换行和标题。这不是文件特别难，而是上下游契约矛盾。

**I-02｜严重：成功状态没有表达结构识别质量。** `studio-import.ts:175–190` 调用文本解析并校验 JSON 形状，随后约第 222 行就记录成功。可读文字、合法数据对象和可编辑简历是三件不同的事，当前被合成一个状态。整段放入“其他内容”可以用于保留原文，不能同时代表模块识别完成。

**I-03｜高：即使保留换行，规则仍不支持自己的正常输出。** 合成回归确认，模块标准名“实习 / 工作经历”“校园与实践”落入 `custom`；`2025.03-2025.06`、`2025/03-2025/06` 和 `2025年3月至今` 没有提取到起止时间。中文姓名只允许首行 2–12 个汉字等有限格式，英文名也没有相应路径。不能只补 PDF 的换行后就宣布导入完成。

**I-04｜严重：解析字段与编辑字段对不上。** `entryHeader` 把“示例大学”写到 `title`，但教育表单把 `organization` 作为“学校”；企业也有同样问题。因此即使教育模块识别出来，主字段仍为空，学校藏在“补充标题”中。通用渲染又能把 title 显示出来，掩盖了字段错位，用户修改后可能重复或改变顺序。

**I-05｜高：导入内容识别与原版式识别没有区分。** 当前导入保留文档已选模板，新文档默认 LapisCV，并未识别原简历模板、页眉或布局。这个默认行为本身不是“自动选错了相似模板”，而是根本不存在原版式重建能力。产品没有把两种能力清楚区分，用户自然期待导入后还是一份结构完整的简历。

**I-06｜高：错误之后缺少可恢复的整理操作。** 原件可以下载，这是已具备的能力；但没有原段落到字段的映射，也没有把一大段内容拆到教育、实习、项目的编辑命令。用户只能新增模块、人工找文字、复制粘贴、删除重复，导入的便利因此被抵消。这里所说的纠错能力不是恢复逐句确认、脱敏或事实审批。

**二、内容模型与功能之间的错位**

**D-01｜高：通用条目容器承载了不同含义，缺少一致的字段语义。** `ResumeStudioEntrySchema` 为所有类型提供 title、organization、role、日期、details 和 body。它可以表示教育或项目，但没有保证各入口按同一含义写入。类型检查证明字段合法，无法证明“学校字段确实是学校”。I-04 是这个问题的实际实例。

**D-02｜高：完整经历、简历表达与补充材料尚未形成清楚的映射。** 原经历和简历虽有不同修订，但内部复用同一 Entry 结构；材料插入会复制整份 entry，模板再依次打印所有 details 和 body。背景、方法、成果、正文可能重复，原经历的全部上下文也会直接成为简历内容。重复的必然程度取决于用户填法，本次没有将其统计成实际发生率。问题在于系统缺少明确的“这一份简历采用了经历中的哪些表达”的表达层。

**D-03｜高：模块识别错误会切断材料闭环。** `captureExperiences` 只处理 internship、project、research、activity。当前导入全部 custom，所以“首次自动积累经历”在这条真实入口中实际没有发生。它不是独立的经历库问题，是导入语义错误向后传播。

**D-04｜高：助手产物也可能再次进入自定义大段落。** `studio-review-service.ts` 在新建经历时，按 `custom` 保存标题和正文；已有经历编辑器的类别选择被禁用。插入简历时又沿用该类别。这意味着“用 AI 整理经历”与“得到适合项目／实习模块的结构”仍是断开的，不能期待多加几个提示词自动补齐。

**D-05｜中：首次收录是否继续同步，依赖隐藏的技术状态。** `capture_open` 允许新条目继续更新经历原稿，checkpoint、导入完成或启动助手等操作会关闭它。之后的同类编辑仅修改当前稿。保留不同方向稿是正确目标，但用户不知道为什么同一个编辑动作在不同时间对经历库的影响不同。本次是代码确认的边界问题，没有声称发现了跨稿覆盖事故。

**三、模板为什么缺少自然的排版感**

自然的排版来自“哪些信息在一组、谁先谁后、哪一行右对齐、什么内容适合侧栏、段落如何接续”等关系。字号只是这些关系中的一个参数。

**T-01｜严重：适配层过早把成熟模板压缩成通用结构。** 40 个 profile 主要用 header、section、entry、columns 等枚举及一组数值描述。`resume-renderer-v3.ts:56` 的 `entryHtml` 为不同模块输出同一套标题、日期、meta、details、body，再通过专用 CSS 重排。已有部分真实结构差异，不能说全部只是换色；但这仍不等于继承 40 套上游完整文档系统。

代表性对照有明确差异：Magic Clean Minimal 的参考组件中，部分模块使用网格组织，教育的学校、学历和专业具有分行关系；Aijob 输出由通用条目控制，信息分行和密度发生变化。JobPilot Classic 的联系方式、教育信息层级也不是直接运行原组件。参考图本身有下述数据绑定问题，因此这些对照足以证明“未完整继承”，不足以给出逐像素还原评分。

**T-02｜高：模板的字段语义被渲染器再次猜测。** 不同 `entry` 枚举会把 degree／major／title 或 role／title 当作主标题，其余字段放 meta。导入恰好把学校放 title 时，与手工把学校填 organization 时会得到不同层级。相同的实际经历不应因为进入系统的路径不同而产生不同版式含义。

**T-03｜高：details 是通用“标签：内容”输出，不是成熟模块的专门编排。** 论文作者、刊物、项目背景、技能类别、成果等，普遍按字段对象顺序打印为段落，再打印 body。它保证字段不容易漏掉，却容易把简历排成数据表单。没有独立字段显示选择，也缺少按模板和模块明确规定的紧凑组合。

**T-04｜高：区域、内容和样式的责任仍交叉。** 栏位存放在 section 内容里，应用模板时通过 `resumeContentForTemplate` 按模块类型和部分模板 ID 改栏位；具体模板区域再由 CSS 特例调整。这使“模板负责布局”和“用户负责内容顺序”的关系不够明确。复杂版式越多，需要的例外越多，继续补 CSS 很难形成稳定的整体。

**T-05｜高：分页主要解决能否放下，没有充分表达阅读组织。** 当前确有标题与首条保持、条目拆分、列表拆分和续页，不能说没有分页引擎。但通用算法依据高度阈值决定整块移页或二分切割文字，所有模板默认 `keepEntriesTogether`；主栏、侧栏分别续排，缺少上游那种明确的逐页区域语义。这里确认的是表达能力限制，不能未经逐页复测就认定现有 40 套全有裁切。

**T-06｜中：图库筛选没有以真实能力为依据。** “照片布局”依据 header 名称的正则，LapisCV、Classic、Magic Clean Minimal 都被排除，尽管现有样张显示了照片。紧凑、长材料也主要依赖分组标签。用户按需求筛选会错过适合的模板，这与单纯增加模板数量无关。

**T-07｜高：模板版本名称不等于还原程度。** 来源、提交、许可证已经登记，属于有价值的工作；但“源码可定位”“输出完整”“版式与原模板接近”是三个不同结果。目前目录数量和版本信息不能替代最后一个结果。

**U-01｜高：默认全部展开，常用操作与低频排版混在一起。** 模块标题编辑、分页、栏位、条目上下移动、隐藏删除、富文本工具及三个 AI 入口重复出现。所需功能并没有因为数量多而变完整；用户写几句话，需要跨越大量控制项。BOSS 截图中的连续表单不能只学成“把全部表单一口气展开”。

**U-02｜高：只有模块折叠，没有单条记录折叠与完整重组能力。** 可上下移动、复制、隐藏、删除，但没有条目跨兼容模块移动、类型纠正、拆分导入内容等路径。没有通用字段级文档定位，点击预览条目只定位到其第一输入框。点击成果正文，可能先被送到项目名称，而不是刚刚看到的句子。

**U-03｜高：整页适配被当作编辑默认，纸张成为缩略图。** `StudioPagedPreview` 按可用高度缩整页，表单独立保持正常字号。`ResumeWorkspace` 每次挂载默认 zoom=page，已有视图记忆只保存 tab、split 和 scroll。用户要不断在“能看全”和“能读清”之间切换，不能用继续减小模板字号解决。

**U-04｜高：移动端是控件放得下，不代表写作舒适。** 360px 没有横向溢出，但顶部多排工具、编辑／预览切换、底部导航一起占据空间，实际输入滚动区只剩 378px。尚未出现软键盘时已如此。本次没有实体设备数据，因此不夸大为已复现键盘遮挡。

**U-05｜高：AI 的局部修改粒度仍偏大，不能整理结构。** `AssistantChangeSchema` 只有 entry_body、entry_title、headline、section_order 四种操作。它不能创建教育／实习条目、拆分记录或纠正专用字段。“局部采用”主要指选某条修改，不是选择段落中的任意局部差异。body 采用通过 `resumeRichText(change.text)` 重建为普通段落，既有加粗、链接、语义列表不一定保留。代码能力已确认；真实模型是否给出好建议未测试。

**U-06｜中：写作材料与简历字段不一致，复用仍带来整理负担。** `ExperienceEditor` 再次使用组织／角色／日期／完整正文的通用字段，不能编辑简历全部专用字段；插入当前稿件又复制整个 entry。材料能被取用，但缺少与当前模块的完整编辑一致性。这会把同一信息的整理成本交回用户。

**已修好而不应继续误报的问题**：本次图库有 40 张卡片，列表独立滚动。滚动到 800px 后选择另一候选，列表仍可见，滚动位置仍为 800px。既有保存恢复、撤销、模板默认值应用和实际内容／样稿区分也有实现，不能因为总体不满意就说它们完全不存在。本次未全量重验其异常路径。

**五、导出与验收为什么没有挡住这些问题**

**Q-01｜严重：输出完整性的起点太晚，无法发现上游语义损失。** `resumeContentManifest` 从当前结构化 content 建清单，PDF/DOCX 再验证这些字段。这个检查有价值；但若 content 已是一段 custom，完整输出这段文字就能通过。它没有原始文档中教育、项目、条目的正确期望，也无法证明字段归属正确。

**Q-02｜严重：导入验收没有断言简历结构。** `resume-quality-import.ts` 导入的恰好是本次复现失败的单页 PDF。它核对邮箱、电话、原件一致性、修改姓名、导出中的若干短语以及重新打开，却没有核对模块类型、记录数量、学校字段和日期关系。因此“导入测试通过”与“导入成大段落”可以同时发生。

**Q-03｜高：120 组矩阵绕过了最脆弱的入口。** 三份材料由程序预先构造成正确的 content，再送入模板和导出。这可以测试排版承载与字段输出，不能覆盖真实 PDF/DOCX 导入后的编辑旅程。数量大不自动扩大测试含义。

**Q-04｜高：上一轮视觉标准主要是无严重损坏，未证明专业排版。** 既有 `visual-review.json` 记录检查所有页联系图，关注明显裁切、重叠、空页；这不等价于确认标题层级、信息密度、模块语义、参考版式还原与编辑舒适度。已有检查不是无效，但完成结论超出了证据。

**Q-05｜高：竞品参照图的数据适配本身也有缺口。** `resume-upstream-reference.ts:10` 给 JobPilot 教育传 school、company 等字段，固定 Classic 源码约第 106 行读取的是 institution，导致参考图缺学校。生成参考图的验证只检查姓名和一个项目短语，不核对完整字段；统一外部容器和字体也不是原产品完整运行环境。不能用一个未校验的参考输入去证明完整还原。

**Q-06｜高：技术进度与产品质量被合并汇报。** 当前路线图、交接称本地主体形成质量候选，并将主要剩余问题列为真实部署、AI 和设备条件；本次复现说明还有日常入口和编辑核心问题。这是需要明确记录的文档／运行冲突，不应拿旧 Gate 阻止继续审计，也不能把本次仅作为新候选功能。

需要区分两份失败：较早的“只有姓名和页码”PDF，已有 S0 记录只能确定对应保存快照没有正文，无法确定浏览器是否曾有未保存输入；本次“整段导入内容”问题则已用实际解析路径复现。不能把前者一并宣称已彻底定位或归咎于同一原因。

**六、对底层是否需要替换的审计判断**

当前可疑的底层不是数据库品牌或页面框架，而是**文档含义、编辑命令、模板区域与输出之间的契约**。即使换成熟项目，如果仍然把整份 PDF 压成一个 body，再经同一个宽泛字段容器转换，新底座也只能排一个大段落；如果只移植模板 CSS，又会丢掉原系统的模块和区域关系。

反过来，保存修订、owner 隔离、原件保留、导出产物、投递稿快照等不因这次问题自动失效。它们是可能继续复用的边界，不能为了修简历把整个求职系统推倒。

所以，“借成熟项目做底座”是合理的可评估方向；但本报告不决定采用哪一个，也不再给出一份先扩模板数量的实施清单。选型需要证明能够保留完整的编辑—文档—输出能力，且适配现有求职材料关系，而不只是让样张好看。导入质量与模板质量必须分别证实，不能互相替代。

**本次应保留的完成标准**

- 结构正确：学校、专业、时间、各段实习和项目是对应对象，而不是文字仍然存在。
- 编辑可完成：能纠正实际导入错误、组织条目和修改正文，保持位置和表达，不必重新制作整份简历。
- 模板可信：同一份真实结构内容在不同模板中形成清晰层级；适配参照本身先经过字段和环境校验。
- 输出可靠：保存与最终文件一致，且不将上游已错位的数据称为完整正确。
- 体验合格：常用操作明显、正文可读，移动端主要空间用于当前任务，功能不能仅靠按钮存在来验收。

这些是审计判据，不是再次增加用户确认关卡。本轮到此完成问题审计，尚未实施修复。
