原工作进程在每次领取前执行一条耗尽任务更新及三条材料状态更新；现在由一个独立循环约每秒处理一次。即使四条任务通道都忙或没有可领取任务，仍会恢复耗尽状态。重试次数、租约、心跳、fencing、删除及新重试保护不变；维护循环失败会使整个worker明确退出，交由既有进程管理恢复。

## 持续负载与故障记录

- 修复前[十分钟](queue-endurance-before-maintenance.json)：600/600助手任务及8次PDF导入完成，排队p95约221ms。协议和模型内容都是夹具。
- 中间一轮[未通过记录](queue-endurance-interrupted.json)：600次计划请求中只完成221次，采样时尚有380项任务未结束。请求生成与采样同时发生约745秒断档，恢复后脚本按过时的计划时间集中补发，最终触发验收超时；这不能作为正常持续流量结果，也不足以判定worker自行崩溃。中断原因没有得到独立确认。
- 现已加入采样/生成中断检测：超过5秒的额外断档会标记环境中断，停止补发，并报告计划、已提交、未发出及未完成数量。中断运行不能记作通过。
- 最终[十分钟](queue-endurance.json)：600/600完成、未发出0、中断0、遗留0；8/8 PDF导入完成。排队p95约192ms，包含模拟模型延迟与观察延迟的完整耗时p95约4.32秒；删除后约169ms中止模拟请求，删除账户不复活。它使用带中断检测的新脚本。
- [超载场景](queue-saturation.json)：12秒提交120次请求，120/120完成，8/8导入完成，约81秒清空。排队p95约64.9秒，完整耗时p95约66.0秒。**证明能恢复积压，不代表高峰用户体验合格。**

所有时长使用同一进程的单调时钟，完成状态每250ms观察。测试使用50ms空闲轮询以增加压力；正常worker默认500ms，所以不能将测试排队数字当成默认生产延迟。两个交互通道和真实用户预算机制保留；没有用真实供应商或扩大线上并发。进程峰值RSS不等于整个系统资源使用量，也不能证明不存在长期泄漏。
