## 运行结构

PostgreSQL 继续负责查询、个人对象、任务和审计；公共聚合跨用户复用，个人比较始终按 owner 鉴权。Web API、collector-worker、match-worker 的数据库权限边界保留。没有引入 Redis、向量库、消息总线、第二套编辑器或另一套认证。

内部供给台由 `pnpm --filter @aijob/platform cli source-console` 启动，只在本机开放。配置建议先在样本上验证，再由内部操作安装；配置安装中断可对照原版本恢复。运行报告以全部保留的计划任务为分母，包含失败、待执行和暂停来源；人工介入按来源报告，首次预览到安装记录为观测耗时而非人工工时。

[最终代码1万岗位/50并发样本](performance-10000-50-v8.json)：热目录p95 428.54ms、热图谱442.63ms；混合负载分别7162.22ms、5369.00ms，Case写入921.23ms。两轮1000个HTTP请求零错误，后台PDF生成后的解析出现1次10秒超时，不能称整轮零错误。首次目录5800.82ms，首个有用概览≤2秒目标未达到。此次后台物化首次安装v3列表投影，触发公共缓存失效；此前[v7](performance-10000-50-v7.json)正常重复物化的混合目录/图谱p95为1034.07/1276.82ms。两种场景都保留，不能用热缓存掩盖更新后的重建成本。

基线 [performance-10000-50.json](performance-10000-50.json) 与后续 v5/v6/v7 均保留。初期 CTE 优化触发 30 秒 SQL 超时已撤回；10 万样本的两次准备失败、一次旧版全量读取中止也保留，不能计为已测新接口容量。之后完成的[10万/100容量测试](performance-100000-100-v4.json)共执行681个HTTP请求、583个错误，多数查询触发30秒超时；阶段截止前未执行到Case写入，不宣称已测该项。后台物化曾出现参数数量超限，已改用单个UUID数组参数；[独立复验](capacity-materialization-repair.json)在10万背景岗位上完成约14.1秒，没有新增岗位版本。该复验不消除HTTP容量限制。
