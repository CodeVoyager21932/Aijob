# 简历导入增量核验（2026-09-23）

本记录接续 K5 本机候选，针对“已有 PDF 导入后内容集中到错误模块”的反馈，只核验文件提取到模块分段。样本均为新生成的合成姓名和经历，没有读取或保存真实个人简历；这不是任意真实 PDF 的盲测合格证明。

## 复现与定位

- 一份首次解析的合成 PDF 在原先的 10 秒进程时限内超时；后续重跑可完成。冷启动是合理推测，但未逐进程证明其唯一原因。
- 在有效版式样本中，使用“教育情况／实习经验／项目成果／技能清单”的 PDF 原本未识别任何模块，10 个正文块留在待整理内容中。根因是 PDF 分栏判断与正文分类各维护一套不一致且缺少上述标题的规则。
- 最初的双栏生成样本有一行学校信息跨过栏位并实际覆盖右侧文字；已把该行换成合理的两行后再评估。不能把重叠版式的失败算作系统对正常双栏的误判。

## 改动

- 抽出 `packages/resume-core/src/import-headings.ts`，让 PDF 几何分栏与模块分类共用相同的精确标题和编号归一化规则；新增四种实际出现的中文标题，解析版本记为 `native-cn-v6`。
- 对“项目成果”增加上下文保护：它是已有实习或项目内部的小标题、且下一行没有明确日期条目时，保留在该经历内，不强行新建项目。
- 结构提取调用的默认时限从 10 秒改为有界的 20 秒；其他旧文本解析时限没有一起放宽。
- 当内容确实无法归类时，导入界面明确说“待整理内容”，并提供已有的分段调整入口；对于提取结果没有汉字的 PDF，说明文字层可能缺少映射及可用替代输入，不把失败识别描述成轻微边界问题。

## 定向结果

`.data/resume-native-import-followup-20260923/` 留有生成脚本、预期清单、4 份 PDF、1 份 DOCX、评估脚本与 `evaluation.json`。样本包含普通单栏、替代标题、右对齐日期、无重叠双栏和研究经历 DOCX。目标是18个模块条目归属；有效版式的修复前稳定重跑为14/18，修复后18/18，五份均无预期条目漏分、无未分类块。PDF 仍标记 `pdf-entry-boundaries` 供用户检查，不误报为完全可信。

工程检查：`resume-core` 导入定向测试10项、`resume-core` 与 `platform` 构建、`platform` 与 `web` 类型检查、改动文件 Biome lint 通过。没有重跑40套模板输出、全仓测试或容量矩阵；本次没有改动模板和导出逻辑。

## 开源样张交叉观察

另用仓库既有的五份开源项目 PDF 样张只读检查，五份均保留为 `unstructured`，没有声称自动分类成功。四份外文样张不在当前中文标题规则的有效范围内；中文的 `billryan-chinese.pdf` 提取出35个块，却没有任何汉字。检查其 PDF 字体资源发现 AdobeHeiti、AdobeSong、AdobeKaiti 的中文字体均缺少 `ToUnicode` 映射，因此当前文字提取器拿不到原本显示在纸张上的汉字。这是文件文字层缺失，不是增加标题别名能修复的问题。界面已在“未结构化且 PDF 提取结果没有汉字”时提供条件式说明，建议回到源 DOCX 或粘贴文字；未实现 OCR，也不伪称已还原中文。

## 仍需实测的边界

这些合成文件由 ReportLab 和 python-docx 生成，其中一份双栏样本在发现物理重叠后调整过；不属于未接触过的多来源真实文档盲集。扫描 PDF、复杂表格、图片化文字和任意作者自定义标题仍可能不能准确分段；原件和来源块会保留，用户可以在当前稿修改或调整识别分段。用户自配 API 的真实 AI、实体设备与正式部署条件仍按 K5 交接单列。业务库和已保存稿件本次未变更。
