## 背景

原 31 岗位 G2 基线已通过；ADR-0017/0018 将范围扩大为 20–30 家企业、300–500 条全部职能实习、中小企业不少于企业数 60% 和岗位数 50%，当前处于 G2 重新验收。截至 2026-07-30：P1–P6 已执行，中信证券上海分公司新增 1 条，其余批次 03–06 来源按过期、主体/申请链冲突或真实 HTTPS `ECONNRESET` 独立暂停；目录总供给 178 条、按 ADR-0021 配额可见 114 条、16 家企业。P6 的 50 条跨职能双标金标已通过，P7 工程与浏览器闭环通过，但目录规模、SME 占比与空库完整恢复未通过。

本计划把"从现在到 G2 重新验收判定"的全部剩余工作固定为可逐步执行的阶段。coco 已确认四项授权口径：**计划范围到 G2 收束为止；本计划批准即为批次 03–06 的预授权；每批抽检由执行方自检自审并留档；鹏扶不补位、备选并入后续批次**。

G2 验收权威清单为 [docs/01-prd-v0.2.md §8](../01-prd-v0.2.md)（9 条）。其中第 2、5、6、7、8、9 条已在既有验收中通过、终局只需全量回归复验；真正未完成的是：
- 第 1 条：目录规模（300–500 条、20–30 家）、中小占比、每来源人工抽检 `min(5, 总数)`；
- 第 3 条：**至少 50 个跨职能分类金标**（jobFamily 分类人工金标，当前 0 条，与已通过的 32 个三轴工程金标是两套东西）；
- 第 4 条：金标中四类守护事件为 0。

## 治理：预授权与委托抽检（执行的第一步是把它写成 ADR-0022）

ADR-0017 第 4 条要求"每批最多评估 5 家、coco 明确批准后才探测"，抽检为 coco 逐条执行。本计划将其修订为（需新增 **ADR-0022** 记录，惯例不允许静默改写）：

1. **批量预授权**：coco 批准本计划即批准批次 03–06 按本计划冻结的名单、请求预算与暂停条件依序执行受控只读核验与首批导入；名单变更、新增批次（07+）、目标修订仍需 coco 单独决定。
2. **委托抽检与自审**（2026-07-26 深夜修订）：每批首批导入后，由执行方逐条比对目录记录与官方原页并出具带原文对照的抽检报告，**自检自审、从严把关，自审通过后即提额**；报告逐批留档，coco 可随时追溯抽查，发现失实即收回授权。自审发现问题按整改或暂停处理。
3. **暂停条件（命中即暂停该家、留痕、不影响其他家，无需请示）**：登录墙/验证码/动态签名或令牌、邮箱域名无法核验主体归属、页面主体与台账主体不一致且无法佐证、无法形成确定性可解析结构、robots 或页面明示禁止且无替代载体。
4. 计划文档入库为 `docs/plans/g2-closeout-plan-2026-07-26.md`，路线面板"下一决定"指向它；每阶段完成后回写勾选状态。

### R1 架构与组件系统性审视（已于 2026-07-29 完成）

- 动机：现有架构与组件划分多为早期"一拍脑门"决定，需要系统性审视。
- 范围：模块边界（catalog / ingestion / sources / matching / insights / profile / identity / tailoring / decisions / workers）、数据模型与 16 个迁移的累积形态、契约层（@aijob/contracts）与前后端接口、任务队列与租约机制、适配器体系的扩展性（后续还有 ~20 家要接）、测试结构与隔离库策略、配置与密钥边界。
- 方法：多智能体并行审查 + 对抗验证（正确性、简化机会、扩展性、一致性四个视角），对照既有 ADR 边界（不得借审视引入被禁基础设施：Redis/向量库/独立搜索/消息总线等）。
- 产出：`docs/evidence/architecture-review-2026-07.md`——发现分级（缺陷 / 风险 / 简化机会 / 不一致），**安全的小改动直接修并过全量工程门**；涉及架构方向的大改动写成 ADR 提案留给 coco 醒后决定，不自行执行。
- 边界：不重写在跑的采集契约与不可变数据链；与批次执行可并行，冲突时批次优先（批次 04 有 8-25 截止）。

执行结果见 [R1 架构审视记录](../evidence/r1/architecture-review-2026-07-29.md)。安全小改动已经通过终局工程门；运行时/数据库角色边界与来源 descriptor/run mode 只形成 ADR-0023/0024 提案，未在本阶段执行。

### R2 前端 UI/UX 重塑（已于 2026-07-29 完成）

- 动机：coco 判断当前前端 UI/UX 质量不足，需要整体调整。
- 步骤：①现状走查（桌面 1280px 与 320px 全页面截图 + 逐页问题清单：布局、层级、密度、配色、字体、交互反馈）；②确定设计基调与设计系统（色彩、字阶、间距、组件规范），**保持产品诚实原则不变**——未知条件透明展示、不显示匹配百分比、无劝退性暗色模式、来源与核验时间可见；③按页面逐个重构：jobs → 详情 → resume → recommendations → insights → tailoring → data-control；④每页收口：320px/1280px 无横向溢出、WCAG 2.2 AA 核心要求、控制台零错误、web 测试更新。
- 工程约束：沿用现有 React + 样式方案，不引入重型 UI 框架依赖；分页面小步提交；真实浏览器验证每一步。

执行结果见 [R2 UI/UX 收口记录](../evidence/r2/ui-ux-closeout-2026-07-29.md)。七个正式页面已统一为“向阳生长”设计系统，真实 1280px 与 320px 验收和全量工程门通过；未改变来源、数据、匹配、AI 或公开边界。

5. 产出 `docs/evidence/g2/g2-reacceptance-<date>.md` 验收报告 → **coco 终局判定（人工卡点，四选一）**：通过 / 带公开缺口通过（需记录判定理由）/ 继续扩容（批次 07+，新决定）/ 修订目标（新 ADR）。

## 不变式（全程有效）

- 不抓综合平台、不绕过登录/验证码/动态签名；robots 与访问政策逐家留痕；`accessPolicyAccepted` 保持 fail、全部来源 `pending_review` 仅限本机、公开 `/v1/jobs` 为 0。
- 企业邮箱必须官方域名（或子域）+ 原句在页；无法核验即 fail-closed。
- 配额压缩只在读取层隐藏并公开缺口；版本与修订零删除；配额恢复只凭合格规模证据。
- 未说明字段保持 `unknown`；工程结果不计为用户价值证据，E0 不变；G0/G1 不在本计划内启动。
- 每阶段收束前全量工程门必须全绿；每批真实探测前先离线夹具测试通过。

## 验证方式

- 每批：适配器单测（含 fail-closed 负例）+ 真实页面互证脚本 → 真实探测运行记录（请求数≤预算、0 拒绝目标、重复探测 `reused=true` 不触网）→ 物化后 DB 断言（entry_scope=实习生、申请链/邮箱、复核项、配额选择）→ 隔离库全量测试/typecheck/build/lint。
- 抽检报告本身即人工验证物；P7 以浏览器全链路回归 + 空库恢复演练收口。
