# ADR-0030：升级为岗位中心求职 OS 并先统一交互架构

- 状态：accepted
- 日期：2026-08-04
- 决策者：coco
- 关联：[ADR-0001](0001-own-core-domain.md)、[ADR-0006](0006-modular-monolith-runtime-boundaries.md)、[ADR-0013](0013-local-ai-recommendation-and-resume-tailoring.md)、[ADR-0027](0027-establish-private-alpha-supply-gate.md)、[ADR-0028](0028-capacity-first-private-alpha-supply.md)、[ADR-0029](0029-official-source-catalog-trust-boundary.md)
- 计划：[Aijob 求职 OS 2.0 升级计划](../plans/career-os-v2-upgrade-plan-2026-08-04.md)

## 背景

现有本地 MVP 已具备可信岗位、资格与证据拆解、简历确认、推荐、受控 AI 修改、DOCX、官方链接、决定状态和数据删除，但页面仍按“岗位、洞察、简历、推荐、数据控制”等独立功能平铺。随着目标扩展到岗位发现、针对性简历、投递管理、文字面试和复盘，继续逐页添加功能会形成多套导航、数据上下文和编辑器，产生拼接式产品与长期维护债务。

coco 已明确选择：立即把产品升级为完整求职 OS；首个交付为单岗位全闭环；采用功能旗标渐进替换；开源项目只做审计后的选择性移植；前人经验采用引用式知识库；不做语音。

## 决定

1. 产品定位升级为“可信官方岗位驱动的完整求职 OS”。一次真实求职项目成为简历、投递、面试和复盘的共同上下文。
2. Aijob 当前 PostgreSQL、模块化单体、任务队列、身份、岗位版本、用户证据、隐私删除和官方来源信任边界继续作为唯一系统骨架。
3. 新增 ApplicationCase 作为岗位工作区聚合；Case 固定具体岗位版本，用户显式决定是否升级到新版 JD。
4. 交互架构必须先于开源能力融合。全局只保留一套侧栏和工具栏；单岗位使用`概览、JD能力、定制简历、投递、面试、复盘`局部标签；右侧检查器承载上下文，不建立 AI 浮窗聊天作为主交互。
5. 首个纵向闭环固定为：可信岗位→能力拆解→证据选择→中文简历定制→导出→投递记录→文字模拟面试→复盘→删除。
6. 采用功能旗标和兼容路由渐进迁移，不进行一次性前端重写。
7. 开源项目按系统骨架、子系统参考、纯组件、行为思路和明确拒绝分级。只有许可证允许且无认证、持久化、遥测和网络副作用的纯组件可以选择性移植；不整仓 Fork、不使用 Git 子模块。
8. 简历语义内容、证据引用和模板布局分离；首轮只做两个中文模板。AI 建议必须逐段接受、编辑后采用或拒绝。
9. 面试首轮只做文字问答、证据引用和复盘；不做语音、视频、录音或实时音频服务。
10. 前人经验只保存 URL、短摘要、适用场景和用户笔记；不抓取全文、不建设社区，也不把经验当成岗位事实。
11. 新增来源扩容在一岗闭环 Gate 前暂停；已授权 canonical 来源仅按现有安全边界维护。100/1000 和 110/1100 目标不取消，产品闭环通过后恢复容量优先扩容。
12. 产品继续禁止匹配百分比、适合度等级、自动劝退、自动投递、虚构经历和未确认事实参与结论。

## 后果

- 优点：所有功能围绕同一求职项目和岗位版本组织；开源项目不会带入第二套系统骨架；移动端可以沿同一信息架构后续实现。
- 代价：100/1000 扩容暂时让位于交互和产品闭环；需要新增领域模型、路由、删除覆盖和兼容层。
- 风险：完整求职 OS 范围较大。通过“一岗全闭环优先、功能旗标、旧页面保留、阶段 Gate”控制范围，禁止同时铺开所有模块。

## 验证

- 全局主导航只有一套，页面刷新和浏览器前进/后退能够恢复工作上下文。
- ApplicationCase 固定岗位版本，新版 JD 不会静默改变已有简历或面试材料。
- 简历、投递、面试和复盘只引用同一 owner 下已确认事实和证据。
- AI 不可用时仍可完成核心准备、导出和记录流程。
- 新实体全部纳入 owner 隔离、TTL、删除墓碑和迟到任务拒绝。
- 不存在第二套认证、数据库、任务队列、AI SDK、岗位真源或用户事实库。
- 公开岗位继续为 0，直到独立公开准入通过。
