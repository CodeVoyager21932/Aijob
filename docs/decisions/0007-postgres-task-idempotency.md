# ADR-0007：使用 PostgreSQL 任务表、至少一次执行和幂等消费

- 状态：accepted
- 日期：2026-07-15
- 决策者：项目维护者
- 关联：来源与采集设计、系统架构、工程交付规范

## 背景

采集、画像解析、匹配和删除都可能超过普通 HTTP 请求时间，并需要在进程中断后恢复。工程 MVP 需要明确投递语义，但当前规模不足以证明必须引入专用消息代理。

## 决策标准

- Worker 中断后任务可接管。
- 重复执行不产生重复岗位版本、匹配或删除副作用。
- 失败有上限、分类和人工处理入口。
- 不增加独立队列基础设施。

## 选项

### 选项 A：HTTP 请求或 cron 内同步执行

- 优点：代码少。
- 缺点：超时、中断、重试和状态查询难以可靠处理。

### 选项 B：立即引入 Redis/Celery 或消息代理

- 优点：具备成熟队列生态。
- 缺点：增加部署、监控和新的故障面，当前没有规模证据。

### 选项 C：PostgreSQL 任务表

- 优点：复用唯一真源、事务和约束，足以支撑 Alpha。
- 缺点：需要自行实现租约、重试分类和队列监控。

## 决定

选择选项 C。任务采用至少一次执行，不宣称 exactly-once：

- 每个副作用请求使用 owner/任务类型作用域内唯一 `idempotency_key`。
- Worker 使用 `FOR UPDATE SKIP LOCKED`、租约、心跳和 fencing token 领取任务。
- 任务基表位于独立 `task_queue` schema；Worker 不直接查询基表，只能通过按角色固定任务类型的 claim/complete 函数访问最小字段，collector 与 match/delete 任务彼此不可见。
- 外部调用在数据库事务外；结果以输入哈希、唯一约束和不可变版本幂等写入。
- 用户任务固定 `owner_epoch`；提交结果时同时校验 owner 未删除、未到期且 epoch 未改变。删除事务递增 epoch 并取消待处理任务，拒绝已领取旧任务的迟到写入。
- 只重试临时网络/限流错误，使用有抖动退避和 `max_attempts`。
- 永久错误和达到上限的任务进入 `dead` 状态并告警。
- API 对异步操作返回 `202 Accepted` 和可查询 `operation_id`。

## 后果

- 正向：无需新基础设施即可得到恢复、幂等和可观察任务。
- 负向：应用需要维护队列表状态机；高吞吐时可能与业务查询竞争数据库资源。
- 后续：测试 Worker 崩溃、租约接管、过期写入、重复请求和死信处理。

## 复审触发条件

- 队列延迟或锁竞争持续影响 Web 查询。
- 任务吞吐、路由或延迟要求无法由 PostgreSQL 满足。
- 引入消息代理的收益有运行数据和迁移计划支持。
