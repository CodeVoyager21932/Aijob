# PRD v0.1：可信岗位匹配工程 MVP

> 状态：Draft / 待验证
>
> 首要用户：处于真实实习或校招投递期、已有基础简历的在校生或应届生
>
> 本版本前提：先完成用户发现与人工礼宾实验；未达到阶段门时，本 PRD 应被修改或暂停，而不是直接扩大开发范围。

## 1. 版本目标

用少量审核后的官方来源和真实岗位，把已经在人工实验中出现价值信号的流程变成可重复运行的最小闭环：

```text
可信岗位发现
  -> 用户粘贴简历文本并确认经历证据
  -> 规则优先的资格与证据匹配
  -> 可解释的投递建议
  -> 企业官方投递页
  -> 最小行为反馈
```

本版本不追求来源数量、通用职业规划或全自动化。每个新增功能都必须能帮助验证“用户是否因此做出更快、更可靠的真实投递决定”。

## 2. 与人工礼宾实验的关系

人工礼宾实验不是本 PRD 中需要开发的功能，而是进入工程 MVP 前的低成本验证。

### 2.1 实验规格

- 输入：20-30 条人工确认有效的官方岗位、5-8 名目标用户的去标识化简历文本、城市/时间/方向/排除条件。
- 处理：人工依据固定模板完成资格判断、经历证据对应、缺口和未知项标注。
- 输出：每位用户 5-10 条带官方链接的候选岗位与解释。
- 观察：用户是否理解、质疑、点击、准备和投递，以及没有行动的真实原因。

详细方法和记录方式见 [产品发现与实验](09-product-discovery.md) 与 [实验卡模板](templates/experiment-card.md)。

### 2.2 进入工程 MVP 的最低信号

- 至少一个清晰用户细分反复出现同一高优先级问题。
- 大多数礼宾测试用户能找到至少一个愿意认真考虑的岗位。
- 至少 3 名用户根据结果进入官方页面并自报完成投递或明确准备投递。
- 用户能够指出来源、资格或证据解释中哪些信息影响了决定。
- 至少记录一项被否定或被修改的产品假设。

若这些信号没有出现，应先修改用户、问题或价值主张，不进入完整工程开发。

## 3. 首要场景与范围边界

### 3.1 本版本服务的场景

用户已经有一份基础简历，也有大致岗位方向和求职约束，但需要从可信的官方岗位中判断哪些值得投递。

本版本不解决“我适合什么职业”或“从零生成一份简历”。没有明确方向或基础简历的学生属于后续研究对象。

### 3.2 最小纵向切片

开发从一条端到端链路开始，而不是并行建设所有模块：

```text
1 个审核来源
  -> 岗位入库
  -> 简单列表/详情
  -> 粘贴简历文本
  -> 确认经历证据
  -> 规则优先推荐
  -> 可解释结果
  -> 官方链接
```

该切片运行和测试通过后，再扩展到数据可行性阶段选定的 3 个代表来源。来源扩展不是首个切片完成的前提。

## 4. P0 功能需求

### 4.1 来源与岗位入库

- `REQ-SOURCE-001`：只有来源注册表中人工审核为允许状态的官方或公开招聘来源可以被采集。
- `REQ-SOURCE-002`：每条岗位必须保留来源类型、原始 URL、首次发现时间、最后验证时间和解析器版本。
- `REQ-SOURCE-003`：采集失败、解析失败和零结果必须是不同状态；来源异常不能静默关闭全部岗位。
- `REQ-SOURCE-004`：岗位需要保存结构化职责、要求、地点、招聘类型、毕业年份/学历等已能可靠提取的字段；缺失值保持未知。
- `REQ-SOURCE-005`：疑似重复、疑似失效和低置信度记录进入人工检查，不自动伪装为确定状态。

### 4.2 岗位列表与详情

- `REQ-JOB-001`：用户可以按城市、岗位方向、招聘类型和毕业年份等核心约束筛选。
- `REQ-JOB-002`：列表默认优先展示近期验证且仍有效的岗位，并显示企业、岗位、地点、来源和有效性状态。
- `REQ-JOB-003`：详情展示结构化职责与要求、原始来源、首次发现时间、最后验证时间和信息不确定项。
- `REQ-JOB-004`：没有可追溯原始链接的记录不得对用户展示。
- `REQ-JOB-005`：用户可以从详情或推荐结果前往经过校验的官方投递页。

首个切片只要求核心筛选，不实现复杂全文搜索、个性化信息流或大量排序策略。

### 4.3 简历文本与经历证据

- `REQ-RESUME-001`：本版本只支持粘贴去标识化简历文本，不支持 PDF、DOCX、图片或压缩包上传。
- `REQ-RESUME-002`：在用户提交前，明确说明数据用途、模型供应商（如使用）、保存期限和删除方式。
- `REQ-RESUME-003`：提取教育、时间、项目、实习、技能和成果等 `ResumeEvidence`，每条证据保留对应原文片段。
- `REQ-RESUME-004`：用户必须能够确认、修改或删除解析结果；未经确认的推断不得作为确定事实参与结论。
- `REQ-RESUME-005`：用户能够删除原始文本、结构化证据、向量/索引和相关缓存。

### 4.4 资格与证据匹配

- `REQ-MATCH-001`：先执行毕业年份、学历、地点、到岗时间等可确定的硬条件判断。
- `REQ-MATCH-002`：硬条件结果必须区分“符合”“不符合”“信息不足”，不能把未知当作符合。
- `REQ-MATCH-003`：再使用规则、词典和必要的语义召回，把岗位要求对应到用户确认过的经历证据。
- `REQ-MATCH-004`：输出“优先考虑”“有条件考虑”“不建议”“信息不足”四类可操作结论。
- `REQ-MATCH-005`：每个结论展示岗位要求、支持证据、缺口、不确定项和投递前建议。
- `REQ-MATCH-006`：AI 只能解释已提供的岗位要求和证据；输出必须通过结构校验，且不得生成不存在的经历。
- `REQ-MATCH-007`：AI 不可用时，岗位浏览、硬条件判断和基础证据匹配仍可使用。

### 4.5 官方投递与反馈

- `REQ-ACTION-001`：平台只链接到企业官方投递页，不代替企业接收申请，也不自动填写或批量提交。
- `REQ-ACTION-002`：记录“查看官方页”和“用户自报已投递”为两个不同事件。
- `REQ-ACTION-003`：用户可以反馈“岗位失效”“推荐不准确”及最小原因分类。

### 4.6 最小运营能力

- `REQ-OPS-001`：运营者可以登记、批准、暂停来源，并查看最近一次采集结果和异常原因。
- `REQ-OPS-002`：运营者可以抽检岗位字段、处理疑似重复/失效/低置信度记录，并追溯到原始页面和解析器版本。
- `REQ-OPS-003`：首轮可通过受保护的脚本、数据库视图和静态质量报告完成，不要求开发完整管理后台。

## 5. 页面范围

| 页面 | P0 内容 |
|---|---|
| 岗位列表 | 核心筛选、来源、最后验证时间和有效性提示 |
| 岗位详情 | 岗位字段、缺失/未知项、原始来源和官方投递入口 |
| 简历证据确认 | 粘贴文本、查看原文对应、确认/修改/删除证据 |
| 推荐结果 | 推荐等级、资格状态、支持证据、缺口、不确定项和官方链接 |

不单独开发营销首页、职业测评页或完整管理后台。封闭测试可以直接进入岗位列表或指定测试任务。

## 6. 关键状态与降级行为

| 状态 | 产品处理 |
|---|---|
| 岗位页面单次无法访问 | 标记待复查，不立即删除 |
| 连续复查失败或官方明确关闭 | 标记已关闭，停止推荐并保留历史状态 |
| 截止时间或资格字段缺失 | 显示未知，不伪造日期或资格结论 |
| 简历字段解析不确定 | 请求用户确认，不进入确定性匹配 |
| AI 服务不可用或超时 | 降级为搜索、硬条件判断和基础证据匹配 |
| 岗位文本疑似包含指令 | 作为不可信数据隔离，不能影响系统指令 |
| 官方链接发生跨域跳转 | 校验最终域名与安全性；无法确认时阻止或警示 |
| 单个来源解析失败 | 隔离该来源并告警，不影响其他来源和已有有效岗位 |

## 7. 数据、隐私与安全要求

- 未登录用户可浏览岗位；封闭测试不以完整账号系统为前提。
- 简历原文不得进入普通访问日志、分析埋点或错误报告正文。
- 默认不把用户简历和匹配结果用于训练模型。
- 岗位网页、简历文本和模型输出都按不可信输入处理。
- 原始 HTML 不直接返回浏览器；外部 URL 采集受域名白名单、重定向和网络访问策略限制。
- 删除请求需要覆盖原文、结构化数据、索引、缓存和可删除备份范围，并保留不含正文的删除结果记录。

具体控制遵循 [安全威胁模型](04-security-threat-model.md)。

## 8. 核心事件与指标口径

### 8.1 最小事件

- `job_list_viewed`
- `job_detail_viewed`
- `resume_evidence_confirmed`
- `recommendation_viewed`
- `official_apply_clicked`
- `application_self_reported`
- `recommendation_feedback_submitted`
- `job_reported_inactive`
- `resume_data_deleted`

事件只记录产品评估所需的最少字段，不记录简历正文或岗位描述全文。

### 8.2 核心结果

- 核心结果：查看推荐后，在约定观察期内通过官方页面完成并自报真实投递的测试用户比例。
- 前置信号：证据确认完成率、推荐到官方页点击率、找到第一个愿意认真考虑岗位的时间、解释有帮助比例、一周内再次使用率。
- 守护指标：无效岗位率、硬条件冲突漏检率、无证据解释率、经历幻觉次数、删除失败数和安全/隐私事件数。

## 9. P0 验收条件

### 数据与来源

- 每个可见岗位都有原始来源和最后验证时间，来源可追溯率为 100%。
- 在约定抽检集中，核心字段准确率达到数据可行性阶段设定的阈值。
- 来源失败能够定位到发现、抓取、解析、规范化或入库阶段，且不扩散到其他来源。

### 匹配与解释

- 固定测试集中，已知硬条件冲突漏检为 0。
- 每条支持结论都能回到具体岗位要求和用户确认过的经历证据。
- 固定测试集中，不得出现生成用户不存在经历的情况。
- AI 不可用时，用户仍可完成岗位发现、硬筛和基础证据匹配。

### 用户与行动

- 目标用户无需讲解即可完成“筛选 -> 确认证据 -> 查看推荐 -> 前往官方页”的任务。
- 官方链接点击与自报投递分开统计。
- 用户可以完成简历相关数据删除，并得到明确结果。

### 运营与恢复

- 运营者能看到来源异常、抽检低置信度岗位并暂停问题来源。
- 一次采集或模型失败不会导致全部岗位不可用。
- 每次测试发布有可执行的回滚方式和验证记录。

## 10. 本版本明确不做

- BOSS、实习僧、牛客等综合招聘平台的数据采集。
- PDF/DOCX/图片简历上传及文件解析。
- 没有明确方向用户的职业探索、职业测评或自动生成完整简历。
- 自动投递、自动填写、模拟登录、验证码处理或绕过访问控制。
- 个性化信息流、社交社区、课程、企业招聘管理和人才库。
- 完整运营管理后台；除非真实运营频率和错误成本证明有必要。
- 为扩大覆盖量提前引入微服务、Kubernetes、复杂消息系统或未知小型招聘项目。

## 11. 发布边界

通过本 PRD 的验收条件只代表可以进入受控私测，不代表具备公开运营条件。公开发布前仍需通过合规、安全、数据恢复、隐私说明、监控告警和灰度回滚等上线门，详见 [从 0 到 1 的产品工程流程](08-zero-to-one-lifecycle.md)。
