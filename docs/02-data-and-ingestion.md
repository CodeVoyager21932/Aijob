# 来源、岗位数据与采集设计

## 1. 设计目标

采集系统的职责是把经过审核的公开官方页面转换为可追溯、可复查的岗位记录。它不负责推荐，不接触用户简历，也不执行来源页面中的任何代码或指令。

## 2. 来源准入

### 2.1 来源等级

| 等级 | 来源 | MVP 处理 |
|---|---|---|
| A | 企业自有域名的公开招聘页面或公开岗位接口 | 优先接入 |
| A | 企业官方招聘系统中的公开岗位页面 | 审核域名和企业归属后接入 |
| B | 高校就业网站发布的招聘信息 | 保留高校来源和企业原始链接；无法确认企业链接时降级展示 |
| B | 企业认证账号公开发布并链接至官方招聘页的信息 | 只把官方落地页作为岗位来源 |
| C | 需要 JavaScript 渲染但无需登录的官方页面 | 经过风险和稳定性评估后接入 |
| 排除 | 需要登录、验证码、账号模拟、解密访问控制或绕过限制 | 不接入 |
| 排除 | 来源不明的转载、群聊截图、个人整理表 | 不进入正式岗位库 |

“公开可见”不是唯一准入条件。来源审核还需要记录服务条款、抓取频率、允许展示的内容范围和退出机制。

### 2.2 来源注册表

`Source` 至少包含：

| 字段 | 说明 |
|---|---|
| `id` | 平台内部唯一标识 |
| `name` | 来源名称 |
| `source_type` | 企业官网、企业 ATS、高校就业网 |
| `organization_id` | 对应企业或高校 |
| `base_url` | 审核后的根地址 |
| `allowed_hosts` | 允许访问的域名集合 |
| `entrypoints` | 列表页、站点地图或公开接口入口 |
| `adapter_key` | 我们自行维护的采集适配器 |
| `trust_level` | A、B、C |
| `crawl_interval` | 合理采集周期 |
| `policy_notes` | 条款、频率和展示限制 |
| `status` | 待审核、启用、暂停、停用 |
| `last_success_at` | 最近成功时间 |
| `parser_version` | 当前解析规则版本 |

MVP 不允许普通用户提交任意 URL 后触发服务器抓取。用户建议的新来源进入人工审核队列，审核通过后才能加入注册表。

## 3. 岗位核心数据模型

### 3.1 原始层

`RawJobSnapshot` 保存重新解析所需的最小原始证据：

- 来源、请求地址、最终地址和响应时间。
- HTTP 状态、内容类型、内容哈希和解析器版本。
- 原始 JSON 或经过安全压缩的 HTML 快照。
- 抓取是否成功、失败阶段和错误分类。

原始内容不直接提供给前台，也不能与模型系统指令拼接后自由执行。

### 3.2 来源记录层

`SourceJobRecord` 表示某个来源中的一条岗位：

| 字段组 | 关键字段 |
|---|---|
| 身份 | `source_id`、`source_job_id`、`source_url`、`apply_url` |
| 企业 | `organization_name_raw`、`organization_id` |
| 岗位 | `title_raw`、`title_normalized`、`description_text` |
| 分类 | `recruitment_type`、`function_category`、`employment_type` |
| 地点 | 国家、省、市、区、远程状态、原始地点文本 |
| 时间 | `date_posted`、`valid_through`、`first_seen_at`、`last_seen_at` |
| 资格 | 学历、专业、毕业年份、工作经验、语言、证书 |
| 实习 | 每周出勤、持续月数、到岗时间、是否可转正 |
| 其他 | 部门、薪资、人数、招聘批次、原始字段 |
| 质量 | 字段置信度、缺失项、审核状态、有效状态 |

原始值和标准化值必须分开保存，不能为了分类方便覆盖原文。

### 3.3 规范岗位层

`CanonicalJob` 用于合并不同页面中指向同一真实岗位的记录。它保留全部 `SourceJobRecord` 关系，不能删除来源差异。

核心关系：

```text
Organization 1---N Source
Source 1---N RawJobSnapshot
Source 1---N SourceJobRecord
CanonicalJob 1---N SourceJobRecord
CanonicalJob 1---N JobVersion
```

### 3.4 版本层

岗位标题、要求、地点、截止时间或申请链接变化时生成 `JobVersion`。版本至少记录：

- 生效时间和内容哈希。
- 发生变化的字段。
- 对应原始快照。
- 变化来自重新抓取还是人工审核。

这样可以区分“同一个岗位更新”和“重复岗位重新发布”。

## 4. 提取优先级

按确定性从高到低执行：

1. 企业公开岗位 API 或稳定 JSON 数据。
2. 页面中的 `schema.org/JobPosting` JSON-LD。
3. 为特定 ATS 或页面模板编写的确定性字段映射。
4. 为单个来源维护的 DOM 选择器。
5. 通用正文提取，进入人工审核。
6. AI 字段补全，只作为低置信度候选，不能覆盖确定性字段。

LLM 不负责发起网络请求、判断访问边界或执行页面中的指令。

## 5. 适配器契约

每个适配器由我们自行编写，并实现最小接口：

```text
discover(source) -> candidate URLs or source IDs
fetch_list(source, cursor) -> raw list records
fetch_detail(source, source_job_id) -> raw detail record
normalize(raw) -> SourceJobRecord candidate
check_active(record) -> active state evidence
```

适配器还必须提供：

- 固定域名白名单。
- 超时、并发和频率限制。
- 分页终止条件。
- 测试夹具，不在单元测试中请求真实网站。
- 解析器版本和字段映射说明。
- 页面变化时的失败信号，而不是返回空数组伪装成功。

## 6. 采集流水线

```text
来源注册表
  -> 调度任务
  -> URL 与网络安全校验
  -> 列表/详情采集
  -> 原始快照
  -> 确定性字段解析
  -> Pydantic 数据校验
  -> 企业与岗位标准化
  -> 精确去重与近似候选
  -> 有效性状态更新
  -> 人工审核队列
  -> 发布到岗位库
```

每个步骤都记录输入数量、输出数量、拒绝数量、失败数量和耗时。任务可以安全重试，重复运行不能重复插入同一来源岗位。

## 7. 去重策略

按由强到弱的证据执行：

1. 同一来源的稳定岗位 ID。
2. 规范化后的官方申请 URL。
3. 企业、招聘批次、岗位编码组合。
4. 企业、标准化标题、地点、正文指纹的近似匹配。

近似匹配只能产生“疑似重复候选”，不能自动丢弃。以下情况即使标题相同也应保留：

- 城市不同。
- 毕业年份或招聘批次不同。
- 部门、岗位编码或截止时间不同。
- 一个是实习，一个是全职。

## 8. 岗位生命周期

```text
discovered
  -> parsed
  -> verified
  -> published
  -> uncertain
  -> closed
  -> archived
```

状态规则：

- 第一次无法访问只进入 `uncertain`，不能立即删除。
- 官方明确关闭、超过明确截止时间或连续复查失败后进入 `closed`。
- 已关闭岗位保留版本和来源证据，但不参与普通推荐。
- 页面恢复后可以重新进入审核，不直接自动恢复推荐。

## 9. 分类设计

分类分成相互独立的维度，避免把所有信息塞进一个标签：

- 招聘阶段：实习、校招、管培生、初级社招、普通社招。
- 用工形式：全职、兼职、实习、合同、其他。
- 岗位职能：产品、运营、内容、研发、数据、设计、市场、销售、职能、制造等。
- 行业：互联网、制造、汽车、金融、教育、消费、医疗等。
- 学生资格：毕业年份、学历、专业、出勤和持续时间。

MVP 允许分类体系不完整，但必须支持版本化和人工纠正。

## 10. 数据质量看板

每个来源至少监控：

- 抓取成功率和连续失败次数。
- 发现、解析、发布、关闭数量。
- 关键字段缺失率。
- 页面结构变化率。
- 疑似重复率。
- 人工抽检正确率。
- 从最后成功到现在的时间。

来源异常只能影响该来源，不能阻塞其他来源或清空历史岗位。
