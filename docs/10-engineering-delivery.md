# 工程交付规范

## 1. 目标

把产品证据稳定地转换成小而完整、可测试、可发布、可观察和可回滚的功能。流程服务质量和学习，不服务形式。

本规范借鉴 [GitHub Spec Kit](https://github.com/github/spec-kit)、[Microsoft Engineering Playbook](https://github.com/microsoft/code-with-engineering-playbook)、[Google Engineering Practices](https://github.com/google/eng-practices) 和 [Twelve-Factor](https://github.com/twelve-factor/twelve-factor)，按当前单人/小团队阶段缩减。

## 2. 功能交付链

```text
问题/实验证据
  -> Feature Spec
  -> 技术计划
  -> 必要 ADR
  -> 可验证任务
  -> 短期分支
  -> 小型 PR
  -> 自动与人工验证
  -> Preview/测试环境
  -> 发布与观察
  -> 结果复盘
```

每一步都能追溯到前一步，避免“代码做完了才寻找需求理由”。

## 3. Definition of Ready

功能进入实现前必须满足：

- 有明确首要用户和问题证据。
- 写清目标结果、非目标和用户流程。
- 验收标准可观察，不依赖“看起来不错”。
- 数据、隐私、安全、AI 和来源风险已检查。
- 明确失败、降级和删除行为。
- 技术方案列出至少一个被拒绝的替代方案，或说明为什么无需比较。
- 任务能形成端到端切片。

缺少这些内容时，任务状态是“待澄清”，不是“开发中”。

## 4. Feature Spec

使用 [功能规格模板](templates/feature-spec.md)，重点写“做什么和为什么”，包括：

- 用户、问题和证据。
- 用户故事与关键流程。
- 功能和非功能要求。
- 非目标和边界。
- 验收、分析事件和守护指标。
- 安全、隐私、可访问性和合规。
- 发布、降级与删除策略。

技术栈不应出现在产品问题定义中，放入技术计划。

## 5. 技术计划

技术计划至少说明：

- 受影响模块和数据流。
- API/Schema 变化及兼容性。
- 数据迁移和回填。
- 失败模式、重试、幂等和并发。
- 测试层级。
- 日志、指标和告警。
- 发布顺序、特性开关和回滚。
- 新依赖及安全准入。

## 6. 决策记录

只有满足以下任一条件才写 ADR：

- 难以逆转或迁移成本较高。
- 会改变安全、隐私或合规边界。
- 会约束多个模块或未来来源适配。
- 存在多个合理方案且未来很可能重新争论。

ADR 使用 [决策模板](templates/adr.md)，记录 Context、Options、Decision、Consequences 和 Revisit Trigger。

小型命名、局部重构和容易撤销的实现不需要 ADR。

## 7. 任务拆分

优先纵向切片：

```text
一个真实用户任务
  + 一批经过核验的代表数据
  + 一个可见用户结果
  + 对应测试和监控
```

本地完整 MVP 按 S0–S5 纵向交付：正式岗位目录、owner/简历、三轴/推荐、AI 优化/DOCX、最终运行验收。人工导入只作为采集失败回退，不替代三个官方来源。避免先分别完成“全部数据库”“全部后端”“全部前端”，最后才发现无法集成。

每项任务应当：

- 最好在 0.5-2 天内完成。
- 有清晰输入、输出和验证方式。
- 不顺便扩大无关范围。
- 完成后主分支仍可运行。

## 8. Git 与代码审查

- 使用短期分支；Codex 创建的分支使用 `codex/` 前缀。
- 一个 PR 解决一个明确问题。
- PR 描述链接 Feature Spec、Issue 和必要 ADR。
- 提交信息说明“为什么改变”，而不仅是文件名。
- 大变更拆成可独立审查且不破坏行为的小变更。
- 即使单人开发，也按 [PR 模板](../.github/PULL_REQUEST_TEMPLATE.md) 做自审；高风险变更邀请第二人或独立 AI 审查。
- 评审重点是正确性、设计、复杂度、测试、安全、隐私和可维护性。

## 9. 测试策略

| 层级 | 本项目重点 |
|---|---|
| 单元测试 | 字段标准化、硬条件规则、三轴判断、状态机、URL 安全判断 |
| 适配器契约测试 | 固定 HTML/JSON 夹具、分页、字段缺失、页面变化、失败不伪装成功 |
| 集成测试 | 三来源离线快照 -> 规范化/去重 -> 目录；PDF/DOCX/文本 -> 解析/确认；证据 -> 三轴/推荐；优化 -> DOCX；墓碑 -> 受限清理 |
| E2E | 找岗位 -> 上传简历 -> 确认 -> 推荐 -> 优化 -> DOCX -> 官方链接 -> 状态 -> 删除 |
| AI 评估 | 模拟 OpenAI-compatible 端点覆盖正常/超时/限流/无效 Schema/无效引用/提示注入，另做一次本地真实冒烟 |
| 安全测试 | SSRF、重定向、会话、CSRF、XSS、对象鉴权、日志泄露、文件类型/ZIP bomb/隔离解析、AI 引用和删除链路 |
| 数据质量 | 来源有效率、字段准确率、重复、失效和版本变化 |

不追求脱离风险的覆盖率数字。核心规则、失败路径和安全边界必须有自动测试。

## 10. CI 门槛

代码出现后，每个 PR 至少运行：

- 格式和静态检查。
- 单元与集成测试。
- 文档内部链接和 Schema 检查。
- 数据库迁移向前/回退或兼容性验证。
- 依赖漏洞扫描。
- Secret 扫描。
- 构建可重复性检查。

主分支持续保持可构建、可测试。不能把持续失败的 CI 当成正常背景噪音。

## 11. 环境与配置

开发早期保持三个逻辑环境：

- Local：开发和固定夹具测试，不访问生产数据。
- Preview/Test：PR 或发布前验证，使用脱敏/合成数据。
- Private Alpha：邀请制真实用户和审核来源，最小权限访问；不等同于公开生产就绪。

遵循配置外置和构建/发布/运行分离：

- 密钥和环境配置不进入代码仓库。
- 相同构建产物通过不同配置进入测试和生产。
- 每个发布有唯一版本，不能在服务器上直接修改代码。

## 12. 发布门

发布前确认：

- Feature Spec 验收完成。
- 相关自动测试、手动 QA 和安全门通过。
- 数据库迁移和备份策略确认。
- 新日志、指标和健康检查可见。
- 发布影响、已知风险、观察窗口和回滚动作明确。
- 隐私政策或用户提示需要变化时已经同步。

## 13. 发布与回滚

- 先在 Preview/Test 验证，再发布生产。
- 高风险能力使用特性开关或小范围用户开启。
- 数据迁移优先采用向后兼容的 expand -> migrate -> contract。
- 发布失败时回滚应用版本；数据无法安全回滚时使用前向修复并提前演练。
- 回滚不依赖临时登录服务器手工改代码。

## 14. 可观察性

### 技术信号

- 请求成功率、延迟和错误分类。
- 采集任务成功、失败、重试和耗时。
- 解析拒绝、字段缺失和来源结构异常。
- AI 调用失败、Schema 失败、耗时和成本。
- 数据库、任务和存储健康。

### 产品信号

- 高质量投递决策、关键漏斗和错误劝退信号。
- 官方链接点击和自报投递。
- 资格、证据、偏好、来源和岗位错误反馈。

日志不得包含简历正文、联系方式、密钥和完整模型提示。

## 15. Definition of Done

功能只有同时满足以下条件才算完成：

- 用户验收标准通过。
- 代码、Schema、文档和测试一致。
- 失败与降级行为已验证。
- 安全、隐私和依赖门通过。
- 可观察信号和回滚路径存在。
- 真实或代表性数据完成验证。
- 发布后结果被记录，并决定继续、调整还是移除。

“代码已生成”不是完成，“本地能跑一次”也不是完成。

## 16. 当前阶段明确不做

- 不建立多团队审批和复杂 Scrum 仪式。
- 不要求每个小决定写 ADR。
- 不追求 90% 以上覆盖率作为形式指标。
- 不提前引入 Kubernetes、服务网格、事件总线和多套搜索集群。
- 不提前引入 Redis、独立搜索、向量库、生产 Playwright 和公共管理后台。
- PDF/DOCX 只按 ADR-0012 实现，不扩展 OCR、图片、旧版 `.doc`、压缩包或复杂版式复刻。
- 本地只实现 OpenAI-compatible 适配层，不硬编码单一供应商；公开启用仍等待供应商、合规和用户增量 Gate。
- 不为未来可能出现的百万级数据设计当前架构。
- 不在没有代码与真实发布需求时创建大量空 CI 工作流。
